## 3. The first key after idle: what runs
- The loop: `running.rs:104-149`. Each pass runs `prefetch`, then `next_wake`, `graphics.drain()` (:114), `update` (:135), `carry_out` (:138), and `draw` (:148).
- `prefetch` (`running.rs:263-290`) returns 0 unless pixels are drawn (:274). At Unicode it does no work, which matches `idle_prefetch_us` p99 ≈ 1.
- `Wakes::waiting` has two implementations:
  - Real: `event_loop/mod.rs:167-180`, a non-blocking `try_recv`.
  - Harness: `Paced::looked`, frames.rs:1092-1110. It returns true once the key is due.
- The harness sleeps in `recv_timeout(wait)` (frames.rs:1044) until the key is due. The key's latency includes the thread's wake from that timeout.
- **No fs watcher, status poll, tick or stale-check** exists on the wake path. `event_loop/mod.rs:9-10`: "nothing polls and nothing ticks". I found no watcher in `graft/src` (grepped `notify|watch|Watcher|mtime`; the hits were only signals and the pool condvar).
- `carry_out` dispatches the commands (`running.rs:201`). A key only reaches the jobs if `update` returned a `ShowRows`.

## 4. `History::outstanding`
- Field: `history/state.rs:241` (`Option<Range<usize>>`). It is cleared when a window lands (`scroll/apply.rs:30`) and set in `ask` (`scroll/query.rs:253`).
- `move_cursor` (`apply.rs:174-208`) ends in `wanted` (`query.rs:200-229`). That asks only when neither the window nor `outstanding` covers the viewport ±2 screens. The ask covers ±3 screens. `drawn` widens the range to strip boundaries at the pixel tier (:235-244).
- Whether the first `j` after idle fires a request depends on where the cursor sits after the scroll. The scroll ends with `PageUp`×60, and I did not compute the window state at that point. **I could not confirm** whether the first `j` fires one. The harness records it: `Watching` logs every `ShowRows` id (frames.rs:780-790).

## Mismatches
- The ticket cites only `docs/log/m1.md:73` ("cause unknown"). But `docs/log/m1.md:77` records that key 37 is "the first key that asks for rows (not first-after-idle…)", with the cause given as "CPU power state after light load (busy core → 6.5 ms, p99 7 ms)". The ticket does not mention that earlier finding.
- The ticket speaks of a "max of 420 keys" (KNOWN_GAPS:447). The code has no max assert. It asserts that no key is ≥ 16 ms (frames.rs:313). The effect is the same, but the "old max assert" in acceptance is really this `late.is_empty()`.
- "Key 37 … if the scenario still exists": it does (frames.rs:200). Key 37 is a scroll key at a 16.7 ms pace, not an idle key.
- The ticket asks for the "input read" and "terminal write" phases. The harness has no input thread: the keys are synthesised in `Paced` (frames.rs:1059). The terminal is an in-memory `Sink` (:752).
- Phases "layout advance / commit reads" run on the history job thread (`history/views.rs:178`, `serve`), not inside the key's frame. A key draws from rows on hand (`waited` check, frames.rs:1004).
- `budgets --phases` has no key loop (see 2), so it cannot serve as the per-key phase tool.
- The Brief names "`History::outstanding`" as a method-like item. It is a field (state.rs:241), which matches MAP.md:856.
