# Scout 03 land-on-result (HEAD ed624165)

## Where the ticket disagrees with the code
- **The ff-pull set-aside rule vs `sets_aside`.** The ticket says `sets_aside()` is true for Pull "when fast-forward and the pulled paths overlap unsaved edits". Today `sets_aside(&self, facts: &RepoFacts)` (`graft-ops/src/operation.rs:1086`) takes `facts` and does **no overlap test**. For Rebase/Rewrite/Checkout it returns `Some` whenever any tracked file is staged or unstaged (`:1087-1105`). It is pure over `RepoFacts`. Could not confirm that `RepoFacts` holds the upstream's changed paths, which an overlap test would need. The ticket's no-arg signature does not match either.
- **`land_on_result(state, kind, new_head)` vs the landing.** `land_on_head` takes no oid: it reads the new HEAD from the refreshed `state.refs` (`banner/stop.rs:148`). `resumed_done` (`banner.rs:877-891`) has no `OperationKind` in scope. Could not confirm where `new_head` would come from on the `Done` path: `Applied` was not read.
- **"Pull previewed?"** No. `p` launches directly (`update/remote.rs:348-368`, `operate::launch(..., Operation::Pull(params))`). The only preview built today is the Ghost Preview, which carries `drawn.set_aside` (`graft-ops/src/preview.rs:410`). Pull has no preview to put `your edits: N files set aside` on.

## Q1. `operated`'s `Done` arm
`update/operate.rs:897-905` handles every kind the same way: `done_status`, `commit_editor::committed`, `refresh_scope`. Nothing is set per kind and nothing touches the cursor or `land_on_head`, so the cursor stays on whatever row the refresh reanchors to (`history_started` reanchors on the old selection, per the comment at `stop.rs:86-89`). `Conflicted` goes to `land_in_resolver` (`:950`) and `Clashed` to `clash::clashed` (`:956`).

## Q2. Continue landing
- `resumed_done` → `finished_lands_on_head(state, &commands)` (`banner.rs:887`, `stop.rs:90-104`). It records the `ReadRefs` id and the `ReadHistory` id from the refresh's commands into `head_landing: HeadLanding{refs, walk}` (`state.rs:328`). `land_on_head` is set only when both reads are present.
- The two reads are spent separately: `refs_answered` (`stop.rs:109`, called from `mod.rs:727`) and `walk_started` (`stop.rs:130`, called from `mod.rs:619`). The walk half is spent by any started walk, not only the named one.
- When both are spent, `land_on_head` (`stop.rs:143-170`) clears `on_working_tree` and calls `history.seek(head, height)`. If the row is not resident yet, it pushes `Command::ShowRows(walk, request)`, so nothing blocks. It drops the landing on an unborn HEAD.
- `mod.rs:741-743` clears the landing (on a refs match, context at the line).

## Q3/Q4. Pull path and set-aside
- The set-aside wrap is in `apply` (`graft-ops/src/apply.rs:233-258`): `set_aside::create` gates on `op.sets_aside(facts)` (`apply/set_aside.rs:65`), then `open_entry`, then `put_aside` (stash store and reset --hard, `set_aside.rs:86+`). Put-back and close are at `apply.rs:356-362`.
- `sets_aside` covers Rebase, Rewrite and Checkout, plus Recover when the branch is checked out (`operation.rs:1088-1090`). Pull falls under `_ => false`.
- Pull runs through the same `apply`. Its remote step is `remote::run` inside `run_plan` (`apply.rs:347`).
- Pull's journal records the head ref, index and tree, and not `refs/stash` (`operation.rs:1458-1463`). Rebase's arm adds `refs/stash` for a set-aside (comment at `:1464`).
- The app side: `remote.running` and `in_flight` (`update/remote/in_flight.rs`). The existing `WouldOverwrite` wording for Pull is at `in_flight.rs:205`.
