# Scout 12: idle-layout-advance (HEAD 96b5547c)

Event-loop basics (loop order, `prefetch`, `Wakes` impls, `outstanding`) are in `scouts/04.md` §3-4. Only new facts are below.

## 1. `StreamingLayout::advance`
- `graft-graph/src/layout/stream/advance.rs:94` `pub fn advance(&mut self, budget: usize, stop: &dyn Fn() -> bool) -> Result<Advance, StreamError<S::Error>>`.
- The budget unit is **rows** (`emitted += shapes.len()`, :115). Each pull is capped at the rest of the current chunk (`room`, :107).
- `stop` is checked between batches (:102) and is also passed into `pull` (:108). A deadline fits as `stop = || Instant::now() >= deadline`, and the call resumes when called again (doc :85). It takes no source args beyond these; the source is owned (`self.source`).
- It always ends with `self.evict()` (:139), so the cache budget holds.

## 2. Who owns the layout
- The layouts live in `Views` (`history/views.rs:35-50`), which is built inside `history::stream` (`history/stream.rs:75`) and runs on a **pool worker thread** as the `ReadHistory` job (`jobs/kinds.rs:67-88`, queued at `jobs/runner.rs:819`).
- The UI thread's `History` holds only a `Window` of rows (`history/mod.rs:9-10`) and talks to the layout through `RowRequest` down an mpsc channel (`runner.rs:817-823`).
- `serve` blocks in `requests.recv()` when idle (`views.rs:189`). **The UI thread cannot advance the layout.** An idle advance has to happen on that worker, triggered by a request or by `serve` not blocking.
- `answer` already advances ≤1 chunk per step, reports `Progress`, and checks `newer()` for a replacing request (`views.rs:241-282`).

## 3. `Wakes`
- Trait: `event_loop/mod.rs:89-104`: `next_wake` (blocking), `waiting` (non-blocking), `mark`.
- There is **no idle-wake or timer mechanism**: "nothing polls and nothing ticks" (`mod.rs:9-10`). Idle work today is only the `prefetch` loop between wakes, and it stops when `waiting()` returns true (`running.rs:263-290`). "Nothing to do" means `prefetch` returns and the loop blocks in `recv` (`mod.rs:177-185`).

## 4. `truncate` fingerprint (:169)
- `StreamingLayout::truncate` (`stream/viewport.rs:166`) calls `cache.truncate(row)` (`layout/cache.rs:272-293`), which removes `laid_out` for every chunk ≥ the cut (:285).
- Then, if the cut is mid-chunk, it calls `cache.renote(cut, &replayed[..])` (`viewport.rs:188-192`). `renote` (`cache.rs:301-308`) calls `note`, which re-inserts a fingerprint for the kept prefix (`cache.rs:160-165`). This has existed since m1/52b (`71a7f898`).
- I found no test named for renote or re-fingerprinting. The only truncate test is `truncate_keeps_the_grid_invariant_and_never_shrinks_the_stride` (`stream/tests.rs:1277`).
- **No caller of `StreamingLayout::truncate` in `crates/graft/src`** (grepped `.truncate(`; the hits were only Vec/String).

## 5. Promotion (:161)
- `serve` calls `views.promote` before answering (`views.rs:196-198`). `promote` opens a new layout and calls `reach` (`views.rs:88-106`), which loops `advance(chunk)` until the anchor has a row (`views.rs:142-161`).
- `reach` checks only `stop` (the cancel token). It does not check for newer requests and sends no `Progress`, so no rows are answered until the anchor is reached. The old layout stays in place until then (doc :81).
- UI side: `sorted` → `history.promote` → `ShowRows` (`update/history.rs:49-66`).

## Carried from 04b: startup events that can queue ahead of key 1
All of these go into the one `ChannelWakes` channel (`JobEvents for Sender<Wake>`, `mod.rs:163-172`), in arrival order:
- **`AppEvent::Started(id, task)`**, one per announced job, sent on the UI thread at dispatch (`jobs/runner.rs:362`). The startup commands come from `update::opening` (`update/mod.rs:98-109`: OpenRepository, CheckSystemGit, ReadHistory, ReadRefs, read_tree) and are dispatched at `event_loop/mod.rs:212-215`, before the loop starts.
- **Produced results**, sent by the worker (`jobs/pool.rs:142`):
  - `Product::Repository` (`kinds.rs:46-58`; `runner.rs:458-469`);
  - `Product::SystemGit` (`kinds.rs:117-131`);
  - `Product::Refs` (`runner.rs:520-525`);
  - `Product::WorkingTree` (`runner.rs:535-540`).
- **History progress**, from the worker via `report` (`kinds.rs:78`):
  - `HistoryUpdate::Started` (`history/stream.rs:54`);
  - one `Progress` per chunk (`views.rs:268-274`);
  - `Window` (`views.rs:~300`).
  - The first request is `ShowRows` from the repository answer (`update/mod.rs:613-614`).
- **Follow-up jobs** that `update` fires from `settle` on every event (`update/mod.rs:175-186`), each adding its own `Started` and result:
  - radar context (`radar.rs:300`), force-push/duplicates probes, journal, `remote::request_at_launch`, `detail::open_explain`;
  - `PromoteHistory` if the order is provisional (`update/history.rs:23-27`; `runner.rs:476`), which yields `Product::TopologicalOrder` (`runner.rs:482`) and then a promotion `ShowRows`.
- **Could not confirm:** which of these actually land before key 1 in a given run, and how long each takes in `update`/`draw`. That needs the per-event timing the ticket asks for. I did not check whether the frames harness uses the same `JobRunner`.

## Mismatches
- The ticket says `pump` calls `History::idle_step` to advance the layout, but `History` (UI thread) holds no layout. The layout is on the job worker (`stream.rs:75`, `views.rs:189`). Advancing it needs a request or worker-side logic.
- The ticket says "no further idle wakes are scheduled", but no idle-wake scheduling exists (`event_loop/mod.rs:9-10`). `Wakes` has no scheduling method.
- The ticket's `advance_until(deadline, /* today's source args */)`: `advance` takes no source args, only `budget` and `stop` (`advance.rs:94-98`).
- KNOWN_GAPS :169 says truncate loses the fingerprint, but `renote` re-notes the kept prefix (`viewport.rs:188-192`, `cache.rs:301`). It is unverified by any named test, and `truncate` has no production caller.
- KNOWN_GAPS line refs :149/:161/:169 match the current file.
