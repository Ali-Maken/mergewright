# Judge by eye: the hint bar is the bottom row of whatever owns the

# the pane's own reserved row, which costs the pane one row of content
# and is what keeps every key from being hidden. `? keys` is never dropped
# (ADR-0037 §4) and sits at the head of the bare keys — the end of the
# row where there are none (ADR-0039, m5/28).
#
# What fills the rest is a **ladder, taken per hint** (ADR-0039's third
# amendment, 2026-09-21). A hint has up to three rungs — full `y sha`,
# short `F3 rend`, bare key `x`. The bar fills from the most relevant
# end, and each hint takes the best rung that still leaves room for the
# hints ahead of it; a hint that will not fit even at its bare key is
# dropped. So the shape to expect is readable verbs at the left thinning
# into a tail of bare keys at the right, the tail turning back into
# verbs as the row gets wider. Nothing steps down as a group: one hint's
# rung says nothing about its neighbour's.
#
# The short rungs come from a table the user wrote, not a scheme. A verb
# it does not name has no short rung and goes straight from full to bare
# key: `m merge`, `r rebase` and `S stash` are the three to watch. A
# squeezed `S stsh` anywhere in these captures is a bug.
#
# Floor: the three most relevant never fall below their floor rung,
# which is their short rung where the table above names one and their
# full verb where it does not. The bar is never all hidden, never fewer
# than three hints, never a key that does nothing, and `.` leads to
# everything the width dropped. The
# room is counted off the bar's own width, not the screen's, so a
# 160-column frame with the pane beside it fills the ~92 cells the bar
# is left rather than falling back to three.
#
# The open question, and why this is a capture rather than a test
# (CLAUDE.md rule 6): does a tail of bare keys after readable leading
# verbs earn its place, or should those hints simply be dropped? Built
# with the bare-key rung in, for the user to answer by eye.
