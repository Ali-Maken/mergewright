# capture_lane_cap_for_docs_shots, asserted). Not a pty capture: the
# terminal is ratatui's TestBackend, so this is a character grid with
# no colour attributes in it — CLAUDE.md rule 5, colour ships
# unverified.
#
# Why: the lane cap was read off the **screen's** width while the
# detail pane stood beside the graph. At 160 columns the graph gets 92
# of them and folded to twelve lanes anyway — the breakpoint for a
# width it does not have. ADR-0039's 2026-09-21 amendment, third
# instance: ask how much room this thing has, not how big the screen
# is (m5/21 item 4).
#
# What right looks like:
#  - **The two frames differ.** With the pane open the graph folds:
#    the header says `+1 lanes` and a `⋮` marker column stands
#    where the folded lane was. With the pane closed the same
#    repository on the same terminal draws every lane and the header
#    says nothing about lanes. That difference is the whole fix — the
#    two used to be identical, because both asked the screen.
#  - One lane, not five, because `Fold::plan` never hides a column
#    with a node on screen: most of these columns hold one. The cap
#    decides only the lanes passing through, which is the point — it
#    is a budget, not a truncation.
#  - With the pane open the subject column starts two cells earlier
#    and every subject is still readable.
#  - Nothing reads as an error on either frame.
#
# What is **not** proven here: colour (rule 5), and whether the graph
# beside the pane reads well by eye — that is yours to judge (rule 6).
# The counts themselves are pinned by
# `lane_cap::the_pane_narrows_the_graph_so_the_graph_folds_more` and
# `view::tests::the_lane_cap_comes_from_the_graphs_room_not_the_screens_width`.
