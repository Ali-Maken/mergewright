## Worker loop: busy-wait, clean stop, races

- **No busy-wait.**
  - `IdleWork::Caught` parks in `requests.recv()` (`history/serve.rs:145-149`).
  - Every other step is one bounded `advance(chunk, stop)` (`views.rs:138`, `:326`).
  - Verified by `a_caught_up_idle_step_pulls_nothing` (0 pulls over 3 caught steps) and `no_wake_after_laid_out`
    (500 ms with no wake). Both pass.
- **Stops cleanly.**
  - The stop closure checks the cancel before the channel (`serve.rs:116`).
  - Senders gone ends the loop as `Cancelled`: `try_recv` Disconnected at `:123`, `recv` Err at `:148`.
  - Test: `a_cancel_stops_the_idle_step_within_one_pull`, which runs through `serve` with the sender still held and
    asserts exactly 1 pull after the answer.
  - Parked with the sender held, cancel is seen only when the sender drops. That was true before 12 too (KNOWN_GAPS
    :148).
- **No race with a request.**
  - A request taken by the stop check is kept in `arrived`, and the loop returns it next (`serve.rs:131-139`).
  - `idle_step` reaches `Caught` (`views.rs:132`, `:146`, `:152`, `:321`) without calling `stop` in that step. So
    `arrived` is empty when the loop parks.
  - A request sent after the last check is buffered by the channel, and `recv` takes it.
  - The one path with no test is Minor 3.
- **No race with input.**
  - Idle work sends only `LaidOut` (tested by `idle_steps_send_no_event`).
  - The batch loop never folds in a key. `ChannelWakes::job_event_waiting` peeks the same `seen` wake that
    `next_wake` returns next (`event_loop/mod.rs:212-214`), and `running.rs:167` requires `from_a_job`.
  - Tests: `queued_wakes_draw_once` and `a_key_behind_queued_wakes_is_drawn_in_its_own_pass`.

## Major

### 1. The heavy tier is red at HEAD: 12c's Part C broke `heavy.rs:217`, and no builder runs heavy tests

**Where:**
- `crates/graft/tests/it/heavy.rs:206-217` sends request 2 with `Promote { anchor: None, .. }` and asserts
  `window.promoted`.
- `until_window_for` (`heavy.rs:312-321`) returns the **first** `Window` for that request.

**What's wrong:**
- Since 12c, a request carrying a promote is answered from the provisional layout first, with `promote` cleared
  (`history/serve.rs:60-64`), and `promoted: request.promote.is_some()` (`serve.rs:230`).
- The promoted window comes later, from an idle step (`views.rs` `promotion_step`).
- `begin_promotion` does not swap a freshly opened layout: `ready_to_swap` needs ≥ one chunk (`views.rs:404`).
- So request 2's first window is provisional every time. It failed in the heavy run and again when re-run alone.

**Why it matters:**
- The heavy tier is a milestone gate, and it has been red since `c7cad495` without anyone seeing it.
- 12's Touches (`12-idle-layout-advance.md:227`) asked for "every reader of `Window`". 12c's Touches (`12c:69-72`)
  did not list `heavy.rs`, which reads `window.promoted` and compiles only under `heavy-tests`.
- 12b's NOTES mention `heavy.rs:315` compiled and clippy-clean, not run.

**Fix:**
- In the test, not the product. The behaviour is Part C's design.
- Make `until_window_for` (or a `until_promoted_window_for`) skip windows with `!promoted` for request 2, so the test
  waits for the swap's re-answer. Then keep the overflow assertion.
- Add `tests/it/heavy.rs` and `synthetic.rs` to the Touches grep for any change to `HistoryUpdate` or `Window`.

### 3. `history/views.rs` grew from 324 to 456 lines, even after the `serve.rs` split (PROMPT.md 6.2)

**Where:** `crates/graft/src/history/views.rs`, 456 lines, all product code. `update/radar.rs` is also over: its
non-test part went from 522 to 565 lines (`mod tests` at `:567`).

**What's wrong:** the limit is about 400 lines. 12c moved `serve`/`answer` out because views.rs was over size, and it
is still over. The promotion machinery accounts for most of the excess:
- `Pending`, `begin_promotion`, `promote` (`:265`), `answered_provisionally`, `abandon_promotion` and
  `promotion_step` (`:315`)

`history/promotion.rs`. That leaves views.rs as "which layouts exist and the idle step". No behaviour change.

  It holds by reading (above), but it has no test.

  arrives and no pull ran after it.

- Fix: drive the example through `begin_promotion` plus `idle_step`, or label its promotion line "synchronous path,
  not the app's".

## Questions

1. **Does the idle advance slow the debug first paint with 50k refs?**
   - `many_refs::first_paint_with_50k_real_refs_is_within_budget` read 1.71 s against the 1.5 s debug guard, run
     alone at load 24–34.
   - The idle advance starts laying out 100k rows on its worker straight after the first `Window`. That is while the
     refs job, which that paint waits on (`many_refs.rs:72-80`, `state.refs.is_some()`), may still be running.
   - The load alone may explain it. I did not run a control, because it needs the idle loop disabled, which is a
     source edit.
   - Release first paint with 50k refs read 39 ms, well inside its budget.
2. **What does scrolling cost after the idle advance reaches the end, on a repository over 128k commits?**
   - With the frontier at the end, scrolling down from the top rebuilds evicted chunks from checkpoints.
   - `max_checkpoints` 64 × `checkpoint_every` 2,000 (`graft-graph/src/layout/stream/mod.rs:51-54`) covers 128k
     rows. Past that the stride grows, and a rebuild replays further.
   - The frames fixture has 100k commits, so it never reaches that. Was the rows-on-hand guarantee measured on git/git
     or larger with the idle advance in?
