## Major

### 1. The 550 guard repeats a check `graft_ops` already makes, against staler data, and its `debug_assert!` can be reached through a race

**Where:**
- `update/operate.rs:114-119` has the `debug_assert!`.
- `update/remote.rs:319-341` is `push_sends_head`, which compares `params.branch` with `facts.head_branch`, the in-memory remote facts.

**What's wrong:**

(a) **The invariant was already enforced where the entry is written, against the real `HEAD`.**
- `graft_ops::apply` reads fresh facts and runs `op.check` **before** the `Pending` line (`graft-ops/src/apply.rs:366-368`, append at :996).
- For a push, that check is `check_push`, which refuses `params.branch != head_branch(facts)` with `Refusal::BranchChanged` (`graft-ops/src/operation/remote.rs:216-221`). The user sees "HEAD moved to another branch since it was read — look again" (`graft-ops/src/operation.rs:552-553`).
- KNOWN_GAPS row 549 (the ticket's "550") itself offered "assert the equality where the entry is written" as a fix, and that assertion already existed. The scout and the builder both missed it.
- The row should have been closed with that line. Instead a second, weaker check was added: it compares against the same memory `push_params` built the push from (`remote.rs:432-438`). When that memory is merely stale, the two always agree and the check passes. When it is stale, only `graft_ops`' check catches the push.

(b) **The `debug_assert!` fires on a state that can actually happen.** Here is the sequence, with the line for each step:
1. A checkout in Graft answers `Refresh::Everything` (`graft-ops/src/apply.rs:741-745`).
2. That refresh re-reads the remotes (`update/operate.rs:1015-1017` → `update/keys.rs:387`).
3. The old facts stay `Ready` while the read runs (`update/remote.rs:226-228`).
4. `P` pressed in that window builds the push box from the **old** `head_branch` (`remote.rs:405-409`).
5. The read lands and replaces the facts (`remote.rs:269`).
6. `Enter` launches the op the box has held since step 4 (`update/confirm.rs:118-123`), so `push_sends_head` returns `Err` and the `debug_assert!` panics.

The same happens with `Ctrl+R` then a quick `P`. Before this group, the same sequence reached `graft_ops` and was refused in words. **In a debug build it now crashes.** Release is fine: it refuses in new words.

I reasoned this from the code; I did not reproduce the timing.

**Why it matters:**
- A crash in debug builds (`cargo run`) where there used to be a correct refusal.
- A gap row "fixed" with a guard that cannot catch the stale case it exists for.
- Rule 2: the cause was already handled a crate down.

**Fix:**
- Drop the `debug_assert!`.
- Either keep `push_sends_head` as a plain words refusal (it then becomes testable through `operate::launch` in the fast tier, which also answers Minor 1), or remove it.
- Close row 549/550 with `graft-ops/src/operation/remote.rs:219-221` and `apply.rs:368` as the line that proves it.

**Question for the conductor:** does the user run daily builds as debug (`cargo run`) or release? That decides whether this is a crash he can hit.

### 3. The "ended by the answer" mark is spent by *the next* working-tree read, not by the read the answer scheduled

- `update/mod.rs:549` calls `reread_disagrees` on any `WorkingTree(Ok)`.
- The `WorkingTree(Err)` arm (:570-575) does not spend the mark, so after a failed re-read it lingers. A much later read that finds a **new** operation (a rebase started in the shell, then `Ctrl+R`) would then say "git says a rebase is **still** in progress".
- The builder's residual is the other half of this: a read scheduled before the resume that lands after the answer.
- Both come from one cause: `ReadWorkingTree` carries no `JobId` (`update/events.rs:98, 421`).
- Neither has been observed, so both are unverified.

**Fix:** file one KNOWN_GAPS row (unverified). The structural fix is an id on `ReadWorkingTree`. It is also the fix for the builder's "working tree trails one stage" question.

### 4. Question: a relaunch into a stop with a clean tree may not keep the pane on the working tree

- `land_on_the_work` sets `on_working_tree = true` without checking `uncommitted_row_shown()` (`update/journal.rs:212` against `update/state.rs:380-385`).
- `selection::reconcile` clears the flag at the end of the event when the row is not shown (`update/selection.rs:75-83`).
- After that, the pane follows the selection onto `HEAD`'s commit.

A conflict resolved to nothing (index == `HEAD`) is exactly Scope 3's "all resolved before the kill" case with a clean tree. The **words** are keyed on `first_conflicted` and would still be right. The pane's landing is not tested there: `relaunch_with_nothing_conflicted` stages a dirty tree. I reasoned this from the code and did not run it.

**Fix:** a third relaunch test on a clean-tree stop, then decide what "lands on STAGED" means when STAGED is empty.

### 9. Two deviations from the ticket are disclosed but no ruling is recorded

- `source_commit` comes from the undo **target's** `refs_before[branch]`, not the push entry's `refs_before[tracking]` (NOTES, 557).
- `repush_lease(&JournalEntry, &str) -> Option<Oid>` replaces `repush_params(..) -> Option<PushParams>`.

**Fix:** one ruling line in the ticket, or an ADR-0038 §4 amendment if §4 names the push entry's `refs_before`.
