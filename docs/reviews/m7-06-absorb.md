## Critical

### C1. A hunk that stays is **lost** when only the index holds it. `stays_unstaged` says it "comes back unstaged"

- **Where:**
  - `crates/graft-ops/src/absorb.rs:85-89` (the flag's doc) and `:179` (the flag).
  - `crates/graft-ops/MAP.md:269`.
  - The cause is `crates/graft-ops/src/apply/set_aside.rs:480-490`: `stash apply S` without `--index`.
  - `docs/adr/0045-…:131` records only "loses the staged/unstaged split".
- **What:** a staged change whose working-tree text was put back, as `add -p` then an editor undo leaves it, exists
  only in the index. The stash's working-tree commit does not have it. After the put-back without `--index`, it is gone
  from the index, the working tree and `stash list`. The clean path drops S.
- **Probe:**
  - `c.txt` staged `C2 staged only`, working tree back to `c2`, plus a placed `t.txt` hunk.
  - The run returned `Ok`.
  - Afterwards: `index-c="c1\nc2\nc3"`, `wt-c="c1\nc2\nc3\n"`, `stash=[]`.
  - The same happens to an index-only mode change (probe `mode+content`).
- **Why it matters:**
  - It breaks M3's promise ("you cannot lose work") silently. Absorb reports success, and the flag tells the preview
    the hunk comes back.
  - `u` restores the index (the undo test asserts it), but only if he notices and nothing has been stacked on top since.
  - Absorb is the one operation whose design leaves staged hunks behind, so it hits this path by design.
- **Knock-on:** every set-aside rewrite (`r`, `a`, `R`) with index-only content runs the same put-back. **Not probed.**
- **Suggested fix (cause):** after a clean put-back, re-apply the stays' patches to the real index with
  `git apply --cached`, one per stay (`Piece.patch` already holds them). That also makes the note's words "stays
  staged" true (Question 1). The other option is to refuse absorb when a stay's text is not in the working tree. Test:
  `an_index_only_stay_survives_absorb`.

## Major

### M1. `blame.ignoreRevsFile` breaks absorb: it fails outright or misplaces
- **Where:** `absorb.rs:349-355`. The blame passes no `--ignore-revs-file`.
- **File missing.** This is the common case: the setting is in global config and the repo has no such file.
  `absorb_map` fails with `fatal: could not open object name list: .git-blame-ignore-revs` (exit 128). Probe, and a
  shell check with `-c blame.ignoreRevsFile=…`.
- **File present.** A hunk on a line that a listed commit changed is blamed past that commit, to f1. The commutation
  check then fails on f1's tree, so the hunk **stays, as `TwoCommitsChangedIt`**, when it belongs in the `reformat`
  commit. Probe `ignore-present`.
- The user's global config has no `blame.ignoreRevsFile` (checked), so this does not bite him today.
- **Fix:** pass `--ignore-revs-file=` (empty clears the config), as `graft-git/src/blame.rs:223` already does for raw
  blame. Add tests for both cases. Then move KNOWN_GAPS M7/06's ignore-revs part to closed.
- **Knock-on:** `graft-git/src/blame.rs:220` ("`blame.ignoreRevsFile` is git's to honour") fails the same way for G-blame
  when the configured file is missing. **Not probed there. It is a question for 18's owner.**

### M2. A staged rename is half-absorbed: the deletion goes into history, the new file stays, and the put-back clashes
- **Where:** `absorb.rs:258` (`--no-renames`) together with `:150-177`. The deleted side is an ordinary hunk.
- **What:** the probe ran `git mv r.txt renamed.txt` on a file f1 added.
  - The map places `r.txt 1..3 → f1` and keeps `renamed.txt` as `NewFile`.
  - Afterwards f1 no longer adds `r.txt`, and the run returns `put staged changes into e3e9945 left conflicts in 1 file`
    with `DU renamed.txt`.
  - The NOTES say `--no-renames` means the new side is "never placed into a commit that had the old path". That half
    holds; the old side is placed.
- **Why it matters:**
  - A rename rewrites history so that the file never existed in the branch, and it leaves him on a conflict.
  - `u` recovers it.
- **Fix:** keep both sides of a rename as stays. Read with renames on (`-M`) and add a `StaysWhy` for a renamed file.
  At the least, a `Deleted` whose content matches an `Added` in the same staged diff should stay. Test:
  `a_staged_rename_stays_whole`.

### M3. A fixup that empties its target stops the rebase with "0 unmerged · resolve"
- **Where:**
  - `rewrite/plan.rs:251-270` plans the fixup without checking the result.
  - `apply/engine.rs:119-125` treats a non-zero exit while rebasing as a stop.
  - `apply/error.rs:98` gives the words.
- **What:** f1 only added `DEBUG`. He stages removing it, and the hunk is correctly placed into f1. git refuses the
  amend ("would make it empty") and stops. Graft says
  `put staged changes into a092e40: 0 unmerged · resolve, then c continues, a aborts`, with `rebase-merge/` live.
  `git rebase --continue` in that state finishes and **keeps f1 as an empty commit** (shell, git 2.54).
- **Why:** "remove the debug line I added in that commit" is an everyday absorb. He lands on a conflict screen with
  nothing to resolve, and continuing leaves an empty commit.
- **Fix:** in `plan`, when the target's tree plus its pieces equals the target's parent tree, plan `drop` for the target
  (with preview words such as `3b2a1f0 becomes empty · dropped`) or refuse in words.
- **Knock-on:** `a` into a commit has the same shape (`plan.rs:192-205`). **Not probed.**

### M4. A staged submodule bump fails the whole absorb
- **Where:** `absorb.rs:159-163`. A gitlink diff has a `Subproject commit` hunk, so it falls through to
  `FileAtHead::read` (`:296-311`), where `cat-file blob <head>:sub` fails.
- **Probe:** `absorb_map` → `Err(… "fatal: git cat-file <head>:sub: bad file")`, although `t.txt` beside it was placeable.
- **Fix:** read the entry's mode and make a gitlink (`160000`) a stay; `NoCommitChangedIt` or its own reason. Test it.
  M7's G-small cares about submodule truth, so it will meet this.

### M5. `apply.whitespace` changes what is absorbed (`fix`) or fails the map (`error`)
- **Where:** `absorb.rs:212-218` (`commit_pieces`) and `:456-462` (`commutes`). Neither pins `--whitespace`.
- **`fix`.** He stages `T2   ` and f1 gets `T2`, with the trailing spaces stripped. The put-back then clashes:
  `UU t.txt` with conflict markers. What was committed is not what he staged.
- **`error`.** `apply --check` exits 128 on trailing whitespace. That is not the "does not apply" code, so the whole
  map fails.
- Both are verified by probe. The user's config sets neither (checked).
- **Fix:** add `--whitespace=nowarn` to both calls.
- **Knock-on:** `operation/stage.rs`, `apply/set_aside.rs` and `preview/stash.rs` also run `git apply`. Not checked.

### M6. The usual "`add -p`, keep editing, absorb" flow leaves conflict markers in his file
- **What:** he stages `T2`, and the working tree has since become `T2 and more`.
  - The rewrite succeeds, then the put-back clashes: `UU t.txt`, with `<<<<<<< Updated upstream / T2 / ======= / T2 and more`.
  - The stash is kept and `u` recovers, so no work is lost. But the conflict is predictable and the flow is common.
- **Cause:** the put-back merges the working tree onto the new HEAD with the **old HEAD** as base
  (`set_aside.rs:480-490`, ADR-0045 §4–§6). Both sides changed line 2 relative to that base.
  - With the **old index** as base, only the working tree changed line 2, so it would merge cleanly.
  - For absorb and `a`, the new HEAD holds exactly the old index's placed lines, so the index is the right base.
- **Suggested:** decide this in ADR-0045 through the conductor. It is the set-aside's design, not absorb's alone.
  Short of that, the preview's put-back forecast should predict the clash before `y`.

### M8. The oracle takes its targets from the code under test, and three placement rules have no test
- **Circular:** `each_target_carries_its_hunks` (`tests/it/absorb.rs:575-583`) looks each target up from `map.placed`.
  It proves the plan carries out the map. It never proves the map's target is "the commit that last changed those
  lines", which is what the ticket header says the oracle judges.
  - Placement correctness rests on 7 hand-picked expectations, all on one 3-commit fixture.
  - Fix: compute the expected target independently in the oracle (a full `git blame` without the range, or
    `git log -1 -L a,b:path main..HEAD`) and assert it equals `map.placed`'s.
- **Mutation run.** 19 mutants of `absorb.rs`/`plan.rs` against `absorb::` (it + lib): **14 caught, 5 survived.**
  - **Survived, and they matter:**
    - *all-below → any-below* (`absorb.rs:434`). Lines split between the range and below it are untested. That is the
      NOTES' deviation 4.
    - *insertion judged by the line above only* (`absorb.rs:367`). The "line below" half of the ticket's insertion rule
      is untested. With the mutant, an insertion between f1's line and a line from main is placed into f1.
    - *every `apply` error read as "does not commute"* (`absorb.rs:465-470`). The rule-3 guard is untested. M5's
      exit 128 shows it is reachable.
  - **Survived, harmless:** the bottom-first sort (`absorb.rs:205-210`), because git apply's offset search places the
    patches anyway; and blame without `<base>..` (`:354`), where lines below the range still land outside it.
  - **Caught:**
    - by a placing test or the tree oracle: dropping the one-commit check, below-only insertion, commutation always
      true, no context lines, `stays_unstaged` false, a missing neighbour judged by one line, the `NewFile` reason, the
      reason when the commutation check fails, the `BeforeYourBranch` reason, `stays_unstaged` = any stay, the below
      context off by one, and rows from the newest target;
    - by a unit test: blame keyed by original line;
    - trivially, by a git error: `^{base}^`.
- **Compared with git-absorb and jj:** neither is installed here, so **not compared empirically**.
  - Analytically: git-absorb places by patch commutation up the stack, not by blame.
  - Graft's blame plus commutation check agrees with it on the rows tested. It differs on insertions at the edge of a
    file: git-absorb can place one that touches a commit's first line; Graft keeps it (NOTES 5).
  - An independent-target oracle (above) is the cheapest stand-in.

## Minor

1. **The "first commit" fallback (`plan.rs:227-232`) is unreachable whenever any local branch exists.**
   - `base_of` → `default_branch_of` → `most_merged_into` (`graft-git/src/branches.rs:174`) picks his own branch, so
     base = merge-base(HEAD, HEAD) = HEAD, the range is empty, and the result is `NothingToAbsorb`.
   - Probe: a repo whose only branch is `work`, with a `y.txt` hunk that w1 made, gives `Refused(NothingToAbsorb)`.
   - The same happens on `main` with no upstream: absorb always refuses, with words saying none of his staged lines
     belong to his branch. See Question 2. Update MAP.md:253 and KNOWN_GAPS M7/06 with it.
2. **Nothing staged gives `NothingToAbsorb`** (`plan.rs:235-242`), whose words end `· c commits them`, although there
   is nothing to commit. ADR-0047 §5 wants "absorb with nothing staged" to have its own words, as `NothingStagedFor`
   does for `a`. No test.
3. **`NoCommitChangedIt` is the reason for binary files, mode-only changes and insertions at the top or bottom of a
   file** (`absorb.rs:65-67`, `:159-161`, `:423`). The words are untrue for a binary file: f1 made `bin.dat` in the
   probe. Split the reason before the preview ticket words it.
4. `stays_unstaged` (`absorb.rs:85-89`) and MAP.md:269 promise that stays come back. Correct them with C1.
5. `absorb_map` takes `_git: &GitVersion` and never uses it (`absorb.rs:100`). The ticket's signature asks for it.
   Say why in the doc, or drop it.
6. `std::collections::BTreeMap` is spelled out 5 times (`absorb.rs:338, 347, 387, 388, 416`) while `BTreeSet` is
   imported at `:31`.
7. `range.get(first..).unwrap_or_default()` (`plan.rs:243`) cannot fail, since `first` comes from `position` on
   `range`. It still reads as rule 3's swallowed failure. Add a comment, or slice after checking.
8. **Performance is unmeasured.**
   - Each candidate hunk makes a fresh temporary index and a full `read-tree` of its target (`absorb.rs:451-455`), so
     N hunks cost N whole-tree reads on the monorepo. One index per target, reused for every `--check`, removes that.
   - `absorb_map` is synchronous and spawns 2 + 3N processes. The keys ticket must run it off the UI thread. That is a
     question for `amend-into-and-absorb-keys`.
9. `StagedHunk.path` holds git's raw bytes as a `PathBuf`. The preview that draws it must sanitise control bytes. This
   is a note for the keys ticket.
10. `parse_blame` (`absorb.rs:387-407`) is a hand parser of git output with no fuzz target. G-blame's
    `blame_porcelain` fuzz target covers a different parser.
11. **Prior art.** The research's git-absorb entry (`docs/research/interactive-rebase.md:131-137`) has no user praise
    or complaints with links, and does not describe its placement rule (commutation, not blame). The choice of blame
    plus a commutation check is recorded only in the ticket's "Decided", not in the note's Prior art (note :39 says
    only "T").
    - Journey 2b (`. motion ⏎ y` = 4, note :77 and :816) is not built in this group (it is the keys ticket), so there
      are no step counts to check yet.

## Questions

1. The note's promise is "a hunk that fits no commit **stays staged**" (note :39, :560, the ticket's title). As built,
   every stay on a file HEAD has comes back unstaged: ADR-0045:131, accepted as M6/0045. C1's fix, re-applying the
   stays to the index, would make the note's words true for free. Take it, or have the preview say "stays, unstaged"?
2. On `main` (or any branch that is itself the default) with no upstream, what is "his branch" for absorb? Today the
   range is empty and every absorb refuses (Minor 1). Options:
   - (a) the commits since the last push or reflog point;
   - (b) the last N commits, as git-absorb does (10);
   - (c) keep refusing, with words that say why.
