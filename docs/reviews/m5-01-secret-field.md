## Critical

### 1. The buffer grows in place, so every reallocation frees an unwiped copy of the password prefix — and the doc says the opposite

`crates/graft-ui/src/text_input.rs:245-252` (`insert`), `:264-271` (`backspace`), `:274-281` (`delete`); the claim at `:206-208`.

`SecretField::insert` calls `self.text.insert(at, character)` on a `Zeroizing<String>` that starts as `String::new()` (capacity 0). `String::insert` grows through `Vec::reserve` → `realloc`; when the allocator moves the block, the old one is freed with its bytes intact. Capacity goes 0 → 8 → 16 → 32, so a 9-character password leaves its first 8 characters in freed heap memory at the 9th keystroke, a 17-character one leaves its first 16 at the 17th, and so on. `insert_str` (a pasted password) goes through the same path one char at a time. zeroize documents this exact limitation on its `Vec` impl ("cannot ensure that previous reallocations did not leave values on the heap"). `Zeroizing`'s `Drop` wipes only the final allocation.

This is the "freed unwiped" half of ADR-0037 §5, still present for any password over 8 characters — the common case. The struct's doc comment (`:206`: "Every mutator below replaces `text` wholesale rather than editing it in place, so the old buffer is always wiped, not just abandoned") is false for three of the four mutators; only `clear` replaces the buffer. A reader trusting that comment would believe the property holds.

Why Critical rather than Major: the group exists to deliver this property, the ticket's inspection tick reads as if it holds, and the code comment asserts it. The leak is narrower than before (prefixes up to the last power-of-two boundary, not the final password), but it is the same class of defect the user asked to close.

Fix (cause, small): reserve once and grow by replacement. `new()`/`clear()` allocate `String::with_capacity(SECRET_CAPACITY)` (say 256 — longer than any real password, and only ever one allocation live). In `insert`, before `self.text.insert(..)`: if `self.text.len() + character.len_utf8() > self.text.capacity()`, build `let mut bigger = Zeroizing::new(String::with_capacity(self.text.capacity() * 2)); bigger.push_str(&self.text); self.text = bigger;` — the assignment drops the old `Zeroizing<String>`, which wipes its whole capacity (zeroize's `String` impl goes through `Vec::zeroize`, which zeroes capacity, not just length). `backspace`/`delete` shrink in place, which never reallocates, so they are fine once the comment stops claiming otherwise. Same treatment for `Clone` is not needed: `to_owned()` allocates exactly once at the right size. Then fix the doc comment to say what is actually true.

## Major

### 1. `SecretField`'s `Debug` prints the length; `PromptField` derives `Debug` and passes it through — the binding condition says length must not be inferable from `Debug`

`crates/graft-ui/src/text_input.rs:364-372`; `crates/graft/src/update/credential.rs:37` (`#[derive(Clone, Debug, ...)]` on `PromptField`); test `crates/graft-ui/src/text_input/tests.rs:531` enshrines `"SecretField(7)"`.

The ticket's conductor block: "Length must not be inferable from the drawn field, its width, a counter, the cursor column or `Debug`." `format!("{:?}", prompt.field)` yields `Secret(SecretField(7))`. `CredentialPrompt`'s own `Debug` omits the field, so an `AppState` dump is clean — but `secret_never_in_debug` (credential/tests.rs:300) prints `prompt.field` directly and only checks that `"hunter2"` is absent, so the length in the output passes the test. The draft signature in the ticket did ask for `SecretField(<len>)`; the conductor's later condition overrides it, and NOTES does not mention the conflict. The comment at `:365-369` ("Even the length is not shown as a bare number") describes the opposite of what the line below it does.

Fix: `write!(f, "SecretField(..)")`. Keep `PartialEq` by length (it is not printed). Change the test at `:531` to assert the exact string `"SecretField(..)"` and add `assert!(!printed.contains('7'))`. In `secret_never_in_debug`, also assert the field's `Debug` contains no digit run equal to the typed length.

### 2. The pulse is a toggle, so the field's resting state is the edit count's parity — one bit of length, on screen and in a committed capture

`crates/graft-ui/src/text_input.rs:223` (`pulse: bool`), `:252/:271/:281/:309` (`self.pulse = !self.pulse`), `:697` (`let first = if pulse ..`); `docs/shots/m4-credential-prompt-in-app.txt:38` shows `◦•••••••` for the 7-character "hunter2", while `docs/shots/m4-credential-prompt-and-hints.txt:50` shows `••••••••` for a view built by hand with `secret: Some(false)`.

A fresh prompt starts at `pulse = false`; after typing a password with no corrections, `pulse == len % 2`. An onlooker who knows the rule (it is in MAP.md and the code) reads "odd" or "even" off the first glyph, and the committed in-app capture already does this for "hunter2". The builder saw this and said so in the conditions block ("two fields with a different total edit count can be at opposite parities"), and the test `eight_glyphs_and_an_identical_pulse_for_any_length` deliberately does not compare absolute rows. That is honest, but ADR-0038 §2's condition is on the response ("must not encode length"), and a persistent toggle does encode one bit of it. The keystroke feedback itself (glyph 0 swaps between two glyphs) is length-independent, so the *mechanism* claim holds — the *state* leaks.

There is no periodic tick in the app (`grep -rnEi '\btick\b|poll\(' crates/graft/src` finds none), so a time-limited pulse is not available to the pure core without adding one. Two cause-level fixes that stay pure:

- (a) Randomise the starting parity per prompt. `credential_needed` is pure and has no entropy; the cheapest honest source is a `bool` carried on `Progress::CredentialNeeded` by the job side (`jobs/askpass.rs`, which already runs on a thread and can read a nanosecond clock's low bit). Final parity is then `start ^ (edits % 2)` with `start` unknown to the observer — zero information. Tests keep the mechanism assertions and add: same field, same start, one keystroke flips glyph 0.
- (b) Make the pulse a one-event flag rather than a toggle: `pulse = true` on an edit, and every other `AppEvent` while the prompt is open (a resize, a job progress, a cursor key) clears it. Cheaper, but during a blocked askpass no other events arrive, so the glyph stays lit after the last keystroke — that no longer encodes parity (it is always lit after any edit), only "you typed something", which is fine. This also fixes the odd case where a `left`/`right` keypress gives no feedback at all.

(b) is simpler and pure; (a) is stronger if the conductor wants the resting frame to carry nothing at all. Either way the two captures should be regenerated so they agree on what "hunter2 typed" looks like, and the conditions block should say which one was chosen. Conductor's call whether the binding condition's wording makes this Critical; rated Major here because the disclosed leak is one bit and the builder flagged it.

### 3. Scope 5(d) was not done and NOTES does not say so: `no_secret_leaked` still does not scan the credential prompt's `Debug`

`crates/graft/tests/it/m4_walk/run.rs:69-91` (unchanged in the diff; `--stat` lists only `vocabulary.rs` under `m4_walk/`).

Scope item 5(d): "the M4 walk's `no_secret_leaked` still passes; add the credential prompt's `Debug` output to what it scans." The scanner still checks the journal, `{event:?}` lines and status lines — not `{state:?}` while a prompt is open. The property is covered at the unit level by `secret_never_in_debug` (so nothing is broken), but the walk-level addition was dropped without a line in NOTES, which lists every other deviation. Rule 4: half-done work is declared, not silently omitted.

Fix: in `run_scenario`'s loop (or in `Recorded`), append `format!("{state:?}")` whenever `state.credential.is_some()` and scan those strings too — a few lines. Or state in NOTES that it was skipped and why.

### 4. `Clone` still copies the secret on every event — the ticket allowed it, the ADR's wording and the conductor's restatement did not

`crates/graft/src/update/mod.rs:63` (`let mut next = state.clone();`), `crates/graft-ui/src/text_input.rs:354-361`.

ADR-0037 §5's defect list is "plain `String`, cloned per keystroke and freed unwiped". This group fixed the first, fixed the third for the final allocation (Critical 1 covers growth), and kept the second: every `update` call — every keystroke, every progress event, every resize while the prompt is open — allocates a second zeroizing copy and wipes the old one. The ticket explicitly permits this ("`Clone` allowed … the clone is its own `Zeroizing`"), the KNOWN_GAPS row that this closes said fixing it "means a zeroing masked field in graft-ui + no per-event clone", and the closed.md row does not mention that the second half stayed. Two live copies of the password exist for the duration of each `update` call; both are wiped; the residual risk is small.

Not a code defect against the ticket. It is a documentation defect: `docs/gaps/closed.md` and ADR-0038 should say the per-event clone remains by decision (the state is cloned per event by architecture — `update` takes `&AppState` and returns a new one — and a zeroizing clone is the accepted cost). If the conductor wants the copy gone, the shape is `AppState.credential: Option<Arc<CredentialPrompt>>` with `Arc::make_mut` on edit — same clone count on keystrokes, none on other events — which is a partial win only; say so in the ADR rather than reopen the row.

## Minor

1. **`text_input.rs:206-212` doc comment is wrong** in the way Critical 1 describes; even after the fix, rewrite it to state the actual rule: "the buffer is reserved once; growth goes through a fresh `Zeroizing` so the old block is wiped; shrinking edits happen in place because they never reallocate."
2. **`text_input.rs:364-370` `Debug` doc comment** contradicts its body ("Even the length is not shown as a bare number" — it is). Goes away with Major 1.
3. **`SecretField::len` is `chars().count()`**, O(n), called from `right`, `delete`, `end`, `PartialEq` and `Debug`. Harmless at password lengths; a one-line comment saying so would stop a future reader "optimising" it into a cached field that then has to be kept in sync.
4. **`credential.rs:339` `prompt.field.clear()` on `Esc` is redundant**: `state.credential = None` on the next line drops the field, which wipes it. Keep it if the intent is defence in depth, but say so; today the comment above it talks about status wording, not the clear.
5. **`credential.rs:324` builds a fresh `PromptField::new(masked)` on `Enter` only to drop it** one line later when `state.credential = None`. `std::mem::replace` with `PromptField::Open(TextField::new(""))` or restructuring to `state.credential.take()` then `prompt.field.into_bytes()` avoids the throwaway allocation and the `masked` read. Readability, not correctness.
6. **`PromptField` has nine one-line dispatch methods** (`credential.rs:55-112`). Fine as-is (the alternative is a trait both fields implement, which the ticket did not ask for), but the doc on the enum should say why it is not a trait: `TextField` and `SecretField` deliberately do not share an interface, because `text()` must not exist on one of them.
7. **The two regenerated captures disagree** on the same scenario: `m4-credential-prompt-and-hints.txt` shows `••••••••` (hand-built view, `pulse: false`, no text ever typed) under a caption that says "hunter2 is 7 characters, but the row still shows 8", while `m4-credential-prompt-in-app.txt` shows `◦•••••••` (hunter2 actually typed). The first caption describes a state the capture did not go through. After Major 2 is settled, regenerate both from the same path and caption them the same way.
8. **`m4-03-credential-masked-*` / `m4-04-credential-username-*` captures still show the 7-glyph mask** (builder flagged this in NOTES; the walk's `--capture` mode needs a pty pass). Should be a KNOWN_GAPS row (unverified, M5 acceptance) so it is not lost — the M5 acceptance group's contact-sheet script (`scripts/contact-sheet.sh`, in this range) will otherwise concatenate stale captures.
9. **Test `debug_redacts_a_secret_fields_text` lost an assertion** (`text_input/tests.rs`): the old `!printed.contains("Some(7)")` check on the cursor is gone. It is moot now that `credential_view` passes `cursor: None` for a secret — but the `FieldView` type still accepts `cursor: Some(n)` with `secret: Some(_)`, and the redaction is what protects that case. Reinstate the assertion with `cursor: Some(7)` in the view so the redaction stays tested.
10. **`Event::Paste(String)` carries a pasted password as a plain `String`** through `graft-core`'s event type and the loop, freed unwiped, and `m4_walk`'s `Recorded.events` records `{event:?}` (test-only). Out of this ticket's scope (input layer) and no non-test code logs events (`grep -rnE 'debug!\(|trace!\(|event:\?' crates/graft/src` finds none outside tests), but it is the one remaining plain-`String` copy on the keypress → git path when the user pastes. Belongs in KNOWN_GAPS as unverified/limitation, expiring M8's architecture pass, so the "never a plain `String`" promise is stated with its real boundary.
11. **Per-keystroke `KeyPress { code: Char(c) }` events** are the same shape of limitation as Minor 10, inherent to any TUI. One line in the same KNOWN_GAPS row.

## Architecture and readability

- Crate rules hold: `zeroize` enters only `graft-ui` and `graft`, both `forbid(unsafe_code)`, `alloc` feature only, one workspace version. No new edge between crates; `graft-git::Secret` untouched, as scoped.
- Pure core vs shell: all new code is pure (`update`, `view`, the widget); no I/O, no threads. `Answer::new` is the one hand-off and it moves, not copies.
- ARCHITECTURE.md needs no change; MAP.md lines for both crates are accurate and unusually complete (the `text_input` line is long — a candidate for splitting `SecretField` into its own bullet, cosmetic).
- No `unwrap()`/`expect()` outside tests in the diff. No swallowed `Result`. No terminal-escape risk: the only new drawn strings are the constant glyphs; `sanitize_line("")` for the secret's text is a no-op kept for the type.
- Git work on the UI thread: none in this group.
- Tests are laptop-safe: all new tests are pure unit tests, no timeouts, no sleeps.

## Summary

Critical 1 · Major 4 · Minor 11. The deviation to `Option<bool>` holds. Ticks: 7 checked, 7 held as worded; two (Debug, pulse) hold against their tick text but not against the user's binding condition. The group is a real improvement over M4 (the final buffer is wiped, the answer is moved not copied, the mask is fixed-width, nothing in the render path reads the length) and should stay merged; Critical 1 and Majors 1–2 are small, cause-level fixes that a follow-up ticket in the same two crates can land in one context.
