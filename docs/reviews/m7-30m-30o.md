### M1. The premise tests prove 2 of the path kinds the put-back now writes over

`crates/graft-ops/tests/it/recover.rs` `u_after_a_file_put_back_brings_back_what_it_replaced`,
`u_brings_back_an_untracked_file_a_put_back_replaced`.

**What's wrong.** The tick is honest: its box names exactly these two tests, and both assert byte-exact content (the
untracked one also asserts `??`). But R1's premise covers more path kinds than they do. The put-back runs
`restore --source=<backup> --worktree -- <paths>` (`graft-ops/src/operation/recover.rs:234-243`). That now writes over:
- **(a)** tracked, unstaged: **tested**.
- **(b)** untracked: **tested**.
- **(c)** staged (the index differs from `HEAD`). R1 names it, and `changed_now` counts it into `replaced`
  (`preview/recover.rs:122-133`). **Untested.**
- **(d)** the `go` direction. The path is absent from the backup, so `restore` (no-overlay, git's default) **deletes his
  current file** (`preview/recover.rs:55-70`, `split` → `go`). This is the only kind where the put-back removes a file
  of his outright. **Untested.**
- **(e)** mode: an executable bit or a symlink. "Byte-exact" is asserted on content only. **Untested.**
- **(f)** a tracked file deleted on disk, which the put-back re-creates. Nothing of his is lost here, but `u` must
  remove it again. **Untested.**

By reading, the mechanism should hold for all of them:
- `Touches { index: false, worktree: true }` (`recover.rs:260-264`), so the index is never written.
- The inverse is `RestoreWorktree { tree: worktree_before, paths: ChangedBetween(after, before) }`
  (`graft-ops/src/undo.rs:333-338`). A path present only on the before side is written back.
- The snapshot's `add -A` records the mode.

That is reasoning, not an observed run. **Unverified as well, and older than this range but newly exposed:** a path
under a clean/smudge filter or `core.autocrlf`. The snapshot stores the *cleaned* blob, so its round trip is byte-exact
only if the filter is idempotent. Before 30o the put-back never wrote over a dirty file, so this path was not reachable
from J.

**Why it matters.** M3's promise is "you cannot lose work". The planner made this premise the part's stop condition,
and the conductor asked for it "for every path kind". Case (d) is the one where the put-back deletes his file, and it
has no test.

**Fix.** Add three real-git tests to `recover.rs`, each put-back then `u`, byte-exact:
- a staged path (assert the index and the worktree both come back);
- a `go` path over a dirty file (the file comes back after `u`);
- a `100755` file (the mode comes back).

Add one KNOWN_GAPS row for the filter/CRLF round trip, marked **unverified**.

### M2. J's find does quadratic work on every frame, unmeasured

**What's wrong.** Every draw of J with a kept find runs this chain:
- `view/journal.rs:73` calls `find::count` (`find.rs:112`).
- `count` calls `kept_hits` (`find.rs:99-107`).
- `kept_hits` calls `hits` (`find.rs:40`). For **every row**, `names` searches the entries linearly for a `●` row
  (`find.rs:64-67`, a `filter` over `newest_first()`, which is itself a fresh `Vec` per call).
- `kept_hits` then calls `index_of` once per hit (`update/journal.rs:81-83`). That is a linear scan which builds a
  `RowKey` for every row, cloning the refname `String` of each `$` row.
- `count` then calls `selected()`, another `index_of`.

The list holds up to entries + `RECORDS_CAP` 2000 + `LOST_CAP` 500 + 50 rows (`graft-ops/src/journal_list.rs:38-40`,
`edits.rs:36`). A query that matches most `$` rows, such as `/main` in a busy repo, costs about hits × rows `RowKey`
builds and allocations **per frame**. `n`/`N` and `⏎` pay the same cost.

**Why it matters.** J is a daily screen (journeys 13–15), and the frame budget fails only under `--release`
(ADR-0021). No perf test opens J with a find, and this round had no release perf run. The risk is unmeasured, not
proven. Rule 1: no one has seen whether it holds.

**Fix.**
- Have `hits` return row indices directly; the `RowKey` round trip exists only because `hits` returns keys.
- Build the entry-description lookup once per call (a `HashMap<&EntryId, &str>`), not once per row.
- Cache the hit indices on `JournalState`, keyed by (query, list rebuild).
- Measure J at `RECORDS_CAP` with a broad query, into `docs/perf/30o-c.txt`.

## Questions (no line proves a defect)

1. **Is it intended that content a put-back replaces is never a J row?** `lost_edits` scans only `Undo`/`Redo`
   entries (`graft-ops/src/journal_list/edits.rs:52-60`). A put-back's replaced copy is reachable through `u` (while
   the put-back is next), and after that through the undo chain or `⏎` on the put-back's `●` row. A discard's copy
   works the same way. So this is consistent, but journey 15 recursing (he wants the *other* version back after a few
   commits) takes more than `J n ⏎ y`.
2. **Should a `$` row on a remote-tracking ref be found by the short name J draws?** `names` strips only `refs/heads/`
   (`find.rs:71`), so `refs/remotes/origin/x` is found by the full refname or `remotes`. Whether J draws `origin/x`
   there is unchecked. If it does, `/origin/x` still matches as a substring, but `/remotes` also matches, which J
   never shows.
3. **Staged path after a put-back.** The index keeps his staged version while the lost edit sits in the working tree,
   so the file reads as both staged and modified. The box says `what's in src/a.rs now is replaced`, which is true of
   the file only. Is that enough, or should a staged path word it differently?
