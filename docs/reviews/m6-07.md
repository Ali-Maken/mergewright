## The judgements asked for

- **F2, the redo of a conflicted stash pop: correct. I found no path that loses work.** `undo.rs:329-345` drops a stash on redo only when the **Undo entry's own** `refs/stash` moved to the pinned commit. `stash_moved_to` is at `:355-373`. I traced each case:
  - Clean pop of `stash@{0}` or `@{1}`: the undo's store moves `refs/stash` to the commit, so the redo drops it by oid (`restore/steps.rs:384`).
  - Conflicted pop, at either index: the undo's store is a no-op, `refs/stash` does not move, and nothing is dropped.
  - Repeated `u`/`U` cycles: each Undo entry carries its own before and after values, so each cycle is decided the same way.
  - `refs/stash` moved to some other commit: nothing is dropped, and the stash stays listed.
  - An undo with no recorded after-value: refused (`Incomplete`).

  The stash commit is pinned throughout. The tests use real git at both indexes, and include a guard for the clean pop of `@{1}`.
- **F10, the modal sweep: structurally complete.** There is one call site, after the `match` (`view/frame.rs:459-461`). The only early return before it is the empty-area one (`:367-371`). Every `state.confirm` setter (13 sites under `update/`) lands in a state that `view_with_graphics` draws through that call. The test sweeps every `GraphOverlay`, the bare graph and the status screen, with an exhaustive `match` in `standing_on`. Two gaps are in Minor 4.
- **F1, the search skip: breaks nothing elsewhere.** The skip is guarded by `next.resolver.is_some()` alone (`update/mod.rs:660`). ## Major

**1. `/` typed into the commit editor goes to the search, not the message. The same happens over the Ghost Preview. Observed.**
- **Where:**
  - `update/mod.rs:655-662`: `search::search_key` runs before `keys::key_event`, and only the resolver is exempt since F1.
  - `update/search.rs:20`: the prompt opens on any `Screen::Graph` with `history` loaded.
  - `AppState::text_field_open` (`update/state.rs:609`) exists for exactly this rule, but `search_key` never asks it.
- **Observed** with two throwaway probes through `update`, at `c309b45`:
  - Commit editor open over a loaded history, then `a`, `/`, `b`: the subject is `"a"` and `search_prompt` is `Some("b")`. The `/` and everything after it leave the message.
  - Ghost Preview open, then `/`: `search_prompt` is `Some("")` and the preview is still open. `preview/tests.rs:207` only passes because it calls `preview_key` directly, not the real path.
- **Inferred, not observed,** from the same lines:
  - the stash message prompt behaves the same way;
  - `n`/`N` with a live search are taken by the search under every modal.
- **Why it matters:** a commit subject like `fix: a/b` loses its tail into an invisible prompt, and `⏎` then runs a search instead of committing. This is daily use. It is not caused by this diff. F1's builder listed the other modals as unverified; they are now verified broken.
- **Fix:** answer the search only when `search_prompt.is_some()`, or when no text field or modal is up (`!text_field_open()`, no preview, no confirm, no resolver). A better alternative is to move the search into the modal chain below the modals. Pin it with a test that types `a/b` into the subject through `update`, and one for `/` over the preview through `update`.

**2. TESTING.md says `U` leaves markers on disk, and the scenario asserts the opposite.**
- **Where:**

- **Why it matters:** the user's checklist describes a result the app does not produce. The spec clause was changed without a "Deviations" entry. The behaviour itself looks right: the redo restores the tree the second `u` found. The box's bold criterion (the `ls-files -u` counts) holds, so I rate this Major and not a false tick. The conductor may rate it higher.
- **Fix:** reword `TESTING.md:2209` to "`U` puts back the unmerged index with `p` as `o` left it". Add a Deviations line to ticket 07.
