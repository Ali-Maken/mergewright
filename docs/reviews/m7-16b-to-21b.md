## Major

### 1. Undo of a `Track` switch leaves tracking config that a later branch of the same name silently inherits
- **Where:** plan `crates/graft-ops/src/operation/history.rs:866-872` (`switch --create <local> --track <remote>`
  writes `branch.<local>.remote/.merge`); undo restores refs by `update-ref` (`crates/graft-ops/src/restore/steps.rs:64`),
  which never touches config. The test `crates/graft-ops/tests/it/switch_rule.rs:230-248` says in its doc comment the
  config stays and calls it harmless, but asserts nothing about it.
- **Verified here** (throwaway repo, git 2.54.0): `switch --create sara/x --track refs/remotes/origin/sara/x`, switch
  away, `update-ref -d refs/heads/sara/x` → `branch.sara/x.remote origin`, `.merge refs/heads/sara/x` remain; a later
  plain `git branch sara/x HEAD` then reports `sara/x@{upstream}` = `origin/sara/x`.
- **Why it matters:** "harmless to git" (10b NOTES, gap row `M7/10b-track`) is wrong. After `u`, a new branch he
  makes with that name tracks the teammate's branch he never chose: `p` pulls Sara's commits into it, `P` pushes to
  her branch (the lease box would show what leaves — the one guard left). He works on dependent branches in a team
  (memory), so same-name branches are the normal case.
- **Fix (cause):** journal the config the Track wrote and have undo remove it (`git config --remove-section
  branch.<local>` when the entry created it), redo re-adding it; or plan Track as `switch --create <local> <oid>` +
  a recorded `branch --set-upstream-to`. Pin with a test asserting no `branch.<local>.*` after `u`. Re-grade the gap
  row from "harmless" to broken with this consequence.

### 2. `JobRunner::dispatch` lost its exhaustiveness: a new `Command` compiles and panics the event loop
- **Where:** `crates/graft/src/jobs/runner.rs:1108` (`command if is_detail(&command)`), `:1133`
  (`other => not_a_job(&other)`), `:1161` (`other => unreachable!("not routed: {other:?}")`). Came in with 21 (and
  16b's merge of two arms) to stay under clippy's 60-line cap.
- **Why it matters:** before, a `Command` variant with no arm was a compile error. Now it builds, and the first
  dispatch panics on the event-loop thread (`event_loop/running.rs:225`, `event_loop/mod.rs:251`) — a crash in the
  user's session instead of a build failure for the builder. The guard `is_detail` (`:1077`) and `dispatch_detail`'s
  own `other => unreachable!` (`:328`) can also drift apart the same way.
- **Answer to the conductor's question:** yes, a real risk, and cheap to close.
- **Fix:** make `not_a_job` exhaustive with no `other` arm — add one arm listing `is_detail`'s ten variants
  (`unreachable!("routed by is_detail")`). Then a new variant must be named in `dispatch` or in `not_a_job`, or the build
  fails. Better still, replace `is_detail` + guard with `dispatch_detail(command) -> Result<(), Command>` returning
  the command it did not take, so the list lives in one exhaustive match.
