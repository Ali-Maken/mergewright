## The M3 promise across the raw-byte paths

What I traced, by reading, at `78f29ea1`:
- **Undo / redo** (`undo.rs` `generic_steps` sets `raw: entry.worktree_raw_before`; `restore/steps.rs`
  `restore_worktree` runs `write_raw` after git's restore; `rollback.rs` `reverse_of` uses `before.worktree_raw`).
  `write_raw` goes through a temp file beside the target and a rename (`restore/raw.rs:174-196`), `create_new`, so a
  crash leaves git's bytes or his, never half. A failed write fails `u` and names the path
  (`undo_bytes.rs:298`). Holds.
- **Set-aside put-back** (30s, `set_aside/put_back.rs`, `returned.rs`): the raw step runs only after a clean apply,
  checks the disk still holds his content first (`same_content_paths`), and `S` is dropped whatever it returns; a
  failure is `AfterState::NotAsTheyWere`, first in `unread`, the entry `Committed`. The bytes stay in the backup's
  `raw/` tree, pinned by the backup ref. Holds (`undo_bytes.rs:521`).
- **Lost-edit put-back** (30w, `apply/lost_edit.rs`): `his_bytes` (:61-71) uses the entry's `raw/` only when its
  `worktree_before` is the backup tree being restored from; `write_back` (:85-107) runs before `finish`, stop swapped
  for one that never fires. Holds (`recover_bytes.rs:110-266`).
- **Snapshot** (`snapshot/raw.rs`): a path is kept raw only when it differs from HEAD, git would convert it, and its
  disk bytes differ from `checkout-index`'s. Any doubt in `autocrlf_converts` counts as "converts" — keeps more, never
  less. A failing read refuses the operation before it runs (rule 3 holds: every `?` in `raw_record` is a
  `SnapshotError`).

**No path found that loses his bytes.** Known limits are filed, not hidden: `M7/30s-raw-fail`, `M7/30w-relaunch`,
`M7/30w-autocrlf-later`, `M7/30q-drift-eol`, `M7/30q-chain`.

Rule 3 scan of every added non-test line (`let _ =`, `unwrap_or_default`, `.ok()`, `unwrap`, `expect`, `Err(_) =>`):
the hits are tests, `restore/raw.rs:194`'s commented `let _removed` (safe: the temp is ours, `create_new`), and
`.ok()` / `unwrap_or` folded into a named error (`restore/raw.rs` `batch_blobs`, `snapshot/raw.rs` `unreadable`).
Clean. Two new `eprintln!` in `Drop` (`snapshot/raw.rs:404`, `snapshot/plumbing.rs:82` pre-existing) report a scratch

## Minor

**m1. `lost_edit::write_back` counts every put-back path, not the ones it writes** (`apply/lost_edit.rs:101-104`,
`files = paths.len()` for `WriteRaw`). `write_raw` writes only the paths the `raw/` tree holds (`restore/raw.rs:31-32`, `kept.retain(… scoped.contains …)`). A put-back of three
files with one kept raw that fails gets "not all written back as they were" (`error.rs:306-310`) when one file is.
The doc at `error.rs:290-291` says `files` is "how many paths the raw step was to write". Fix: count the paths
`raw` holds (`tree_entries` is already `pub(super)`), or word the plural without "all".

**m2. `AfterState::NotAsTheyWere`'s doc says set-aside only** (`apply/error.rs:280-284`: "A set-aside put-back
brought his edits back…"); 30w made the lost-edit put-back its second producer (`apply.rs:409`, `lost_edit.rs:105`).
And `ApplyError::Journal.kept` is documented as "where a set-aside's edits are" (`error.rs:37-47`) while
`apply.rs:419` now puts the raw failure's words there. Fix: two doc edits.

**m3. `raw_tree` passes every kept path on one command line** (`snapshot/raw.rs:279-287`, `hash-object -w
--no-filters -- <paths>`). A very large kept set (a CRLF re-normalisation touching thousands of deep paths) can pass
ARG_MAX (1 MiB on macOS); the spawn fails, the snapshot fails, and every operation refuses until the tree is
smaller. `same_content_paths` already uses `--stdin-paths` (`restore/raw.rs:72-125`). Fix: the same here.

**m4. `write_his_bytes`'s temp name appends 18+ bytes to his file name** (`restore/raw.rs:177-178`,
`.graft-raw-<pid>`). A name within 18 bytes of NAME_MAX (255) makes the `create_new` fail every time: `u` fails and
names the path, so no loss, but no in-app way past it either. Fix: a short fixed-length temp name in the same
directory (`.graft-<n>`), or a question for the planner.

## Questions

**Q1.** After a raw-step failure the words end "its exact bytes are in the backup" (`error.rs:301-305`) with no
in-app route to them (ruled 2026-10-01, gap `M7/30s-raw-fail`). For the lost-edit put-back, `u` then `J n ⏎ y`
would seem to retry it (not tried). Should the lost-edit words say so?

**Q2.** 30t's ladder (`operation.rs:1137-1187`) goes from `<top>/…/<name> (ignored) is in the way` to
`…/<name> is in the way`. At 80 columns the guard picks `…/session-cache.json is in the way · move it aside first
· esc dismiss`; `src/…/session-cache.json is in the way` (no tag) is not a rung, though it would fit and says
where. By design per the ADR-0049 amendment, or an omitted rung?

**Q3.** `in_the_way_status` measures `words.reason.width()` (`update/operate/failure.rs:195`) on the path as
stored; the footer sanitises control characters before drawing. A path with a control byte could measure narrower
than it draws and be cut with `…`. Not reproduced.

**Q4.** 30p-d refreshes J's find hits on every `rebuild` (`update/journal.rs:276`, `:333` → `refresh_hits`). The
`journal_find` frames scenario types the find only after stages 2–3 have settled (`frames/journal_find.rs:11-14`:
"The wait … Not measured"), so a find kept open while rows arrive is unmeasured. Worth a scenario?

**Q5.** `autocrlf_converts` (`graft-git/src/snapshot_reads.rs`) reads repo and global config through gix; config
passed by `GIT_CONFIG_COUNT`/`GIT_CONFIG_PARAMETERS` (which the `git` spawns do honour) is not considered.
Unverified either way — does gix's open read them?

**Q6. Three fuzz targets ran far past `-max_total_time=60`** (`line_log` 590 s, `parse_file_list` 397 s,
`parse_porcelain_v2` 1001 s; exec/s fell to 55–339 against ~10 000 for the others). libFuzzer checks the total time
only between inputs, so a single slow input can hold it; or the machine was loaded (another agent's work ran
beside it). Unverified which. If it is a slow input, PROMPT.md 7.1's 60 s bound is not laptop-safe for these
parsers — worth a `-timeout=` per input in the run line and a look at the slowest corpus entries. No parser changed
in this range.
