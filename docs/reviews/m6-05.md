## Major

### 1. The whole-file card's footer draws four keys that silently do nothing, and a fifth that promises the wrong thing

**Where:**
- `view/rows.rs:399-404` always answers `Resolver { base: true, restart: true }`.
- `graft-ui` `resolver_list` then draws `B base  e edit  n next  N prev  ⏎ resolved  M mergetool  d start over`.

**What each key does on a whole-file card** (`file: None`):
- `B` returns silently at `update/resolver.rs:497-499` (`let Some(file) = open.file.clone() else { return; }`).
- `⏎` returns silently at `resolver.rs:582-584`.
- `n` and `N` return silently at `resolver.rs:538-540`. The user can't skip a card to reach the next conflicted file. Only `Esc` works.
- `d` opens a box saying "the conflict comes back with all its markers" (`resolver.rs:665`). After confirming, `ops` refuses `NotMarkerShape` for every whole-file shape, because the restart gate is `has_markers` (`graft-ops/src/operation/conflict.rs:248-254`).

**Why it matters:** this is the m5-03 review's Critical 2 class again: the bar teaches keys that do nothing (CLAUDE.md status rule; hints.rs module doc). The key sweep misses it because its only resolver state has `file: Some` (`update/tests.rs`, `resolver_on_screen`, :4173). Scope 3 asked for the `d` refusal in words on a whole-file card. No test covers it.

**Fix:**
- Carry the card's shape into the hint context, for example `Resolver { base, restart, whole_file }`, or pass `base: false, restart: false` on a card.
- Drop `⏎`, `B` and `d` from a card's list. `o`/`t` already mark it resolved (design note line 173).
- Make `n` on a card cross to the next conflicted file, as it does at a document's last block.
- Refuse `d` in words before opening the box when `!how.has_markers()`.
- Add a whole-file card state to the `every_key_the_bar_draws_is_answered` sweep.

### 2. A base load that lands after a take overwrites the taken document

**Where:**
- `take_side` refuses only while `open.job` is busy (`update/resolver.rs:357,363`). It ignores `base_job`.
- `toggle_base` sends a clone of the document taken at `B` time (`resolver.rs:516`).
- `base_loaded` replaces the document unconditionally (`resolver.rs:1009`, `open.file = Some(file)`).

**The sequence:** `B` → `o` before the base lands → the take lands (block taken, on disk) → the base lands and puts back the pre-take document with bases attached.

**Why it matters:**
- The screen shows the block open while the file on disk has it taken.
- `⏎` is refused ("conflicts still open") against the stale document.
- The next take fails the fingerprint check (`WriteError::Changed`, "the file changed on disk since it was read", `graft-git/src/conflict.rs:728`). The user sees it as a **problem** notice about an outside edit that never happened.
- Nothing on disk is lost: the fingerprint guard holds. But the resolver's one promise, "what is on screen is on disk" (design note, Hard-to-reverse 2), is broken.
- The same stale-overwrite happens if `e` is pressed while a base load is in flight. `handed_back` (`resolver.rs:914-928`) never clears `base_job`, so the base answer can land over the fresh re-read.

**Fix:** refuse takes (and `e`/`M`/`d`) while `base_job` is busy, or have `base_loaded` drop an answer whose source document is no longer the one open (compare the `Arc` pointer or a generation counter). Clear `base_job` in `handed_back` and `conflict_arrived`. Add a test: `B`, then `o` before pumping, then assert the block stays taken.

### 3. `d` can launch a second git write while one is already running

**Where:**
- `restart_box` checks only `open.job` (`update/resolver.rs:642`), never `state.operating`.
- The confirm's `RestartConflict` arm launches unconditionally (`update/confirm.rs:144-160`).
- Compare `whole_file_take` (`resolver.rs:433`) and `mark_resolved` (`resolver.rs:592`), which both refuse while `operating` is set.

**The sequence:** a whole-file `o`, or `⏎`'s `Stage` → `d` → `Start over`. `operate::launch` overwrites `state.operating` with the second id.

**What follows:**
- `operated` drops the first write's answer because `state.operating != Some(id)` (`update/operate.rs:738`), so its refresh and status are lost.
- `operate_answer` still runs `resolved_advance` for it whenever the outcome was `Done` (`update/mod.rs:433-449`). The resolver moves to the next file while the restart puts markers back into the file it just left.
- Two `apply` calls run concurrently on one repository: journal fold, chained backup, `index.lock`.

**Why it matters:** this is concurrent writes on the user's index behind one busy line.

**Fix:** refuse `d` in `restart_box` while `state.operating.is_some()` or `open.staging.is_some()`, with the same words `⏎` uses. Better, also guard the confirm's accept, since state can change while the box is open. Add a test.

### 4. A whole-file card holds the entire file, uncapped, deep-copied on every event and sanitised whole on every frame

**Where:**
- `worktree_lines` reads the whole file with no size cap (`jobs/conflict.rs:117-135`). The marker path caps at `MAX_BYTES` = 8 MiB (`graft-git/src/conflict.rs:681,707`).
- The lines are stored as `WholeFileShape.lines: Vec<Vec<u8>>` (`update/resolver.rs:128`), not behind an `Arc`.
- `update` does `state.clone()` on **every** event (`update/mod.rs:107`), so every keypress and tick copies the file.
- `whole_file_view` sanitises every line on every frame (`view/resolver.rs:83-87`), not just the visible window.
- A binary `UU`/`AA` card also renders its bytes as lossy text "lines".

**Why it matters:** a conflicted binary asset or a large generated file (50–100 MB is ordinary) freezes the UI thread. PROMPT §1.2's frame budget is unmeasured on this path; no test covers a large whole-file card.

**Fix:**
- Cap the read like the text path, or read only the first screenful.
- Show no content for a binary card, only something like `binary · 4.2 MB`.
- Store the lines as `Arc<[…]>`.
- Sanitise the visible window only, or sanitise once when the read lands.

### 5. `whole_file_and_restart_fold_into_live_entry` is named and documented for behaviour it does not exercise

**Where:** `tests/it/resolver.rs:842-854`.
- The doc comment says both writes "run *inside* the merge's own live operation … the merge's one `Pending` entry is what `u` still undoes".
- The fixture's merge was made with raw git (the test's own comment at :850-853). No `Pending` entry exists, so nothing folds. The path taken is `resume.rs:92-97`'s "no entry of Graft's to chain onto … nothing to keep".

**Why it matters:**
- It is a behavioural claim with nothing under it (rule 1). A reader takes this test as proof of app-level folding.
- It also hides that in a shell-begun merge, a whole-file `t` or a `d` takes **no** backup. That is the ops trade-off m6 g03 review M2 already raised, but nothing on the app side names it.

**Fix:** either rename the test (for example `no_entry_added_in_a_shell_begun_merge`) and correct its doc comment, or add the fold test the name promises: start the merge through the app (`m` on a conflicting fixture), then do a whole-file `o` and a `d`, then assert one `Pending` entry and its chained backup ref. Keeping both is best.

### 6. `update/resolver.rs` is 1229 lines, three times PROMPT §6.2's ~400-line limit, and this group grew it by 320

**Where:** `crates/graft/src/update/resolver.rs`: 909 lines at `f7a11b5`, 1229 at `e6c92cd`. The test file `tests/it/resolver.rs` is 1806 lines.

**Why it matters:** §6.2 is a hard rule. The file now mixes five concerns: keys, whole-file resolution, the base load, the restart, and job answers.

Suggested modules: `update/resolver/whole_file.rs` (`WholeFileShape`, `whole_file_keys`, `whole_file_take`, `whole_file_both_refused`), `…/base.rs` (`toggle_base`, `base_loaded`), `…/restart.rs` (`restart_box`, `restart_landed`), and `…/answers.rs` (the `conflict_opened` … `resolved_advance` group). Split the test file the same way. Use `codebase-design`.
