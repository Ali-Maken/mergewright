## Major

### M1. The hit-test measures against a `GraphView` the frame never draws

`crates/graft/src/view/hit.rs:46` builds `graph_view(state, now_seconds)` and
hands it to `row_at`/`badge_spans`. `graph_view` sets
`icons: Icons::default()` (`crates/graft/src/view/rows.rs:58`) and
`compaction.max_lanes: DEFAULT_MAX_LANES` = 8 (`rows.rs:253`,
`config/types.rs:172`). The frame then **overrides both** before drawing:
`crates/graft/src/view/frame.rs:246` `screen.icons = session.icons;` and
`:247` `screen.compaction.max_lanes = max_lanes_for(graph_columns(..),
session.max_lanes)` — which is 10 at 100–159 columns and 12 at 160+ when
`graph.max_lanes` is unset (`graft-ui/src/graph_screen/layout.rs:389-414`).

Consequences, both real:

- **Lane cap.** On a screen with 9–12 lanes at ≥100 columns the frame draws
  them unfolded and the hit-test folds them at 8, so `graph_width` — and
  therefore `Columns::subject_x` — differ, and every badge span the hit-test
  reports is shifted left of where the badge is drawn by the folded lanes'
  width. Same again for any configured `graph.max_lanes ≠ 8`.
- **Icons.** With `ui.icons = nerd`, `badges::separator` is two cells, not
  one (`badges.rs:138-143`), so every badge after the first on a row is
  drawn one cell right of where the hit-test puts it; tag badges also change
  width (`badges.rs:106-109`).

The renderer/hit-test agreement test the ticket asked for
(`graph_screen::tests::badge_spans_match_the_drawn_cells`) lives in
`graft-ui` with **one** view on both sides, so it cannot see this. The
integration test's comment claims it would — `name_and_drag.rs:293-296`:
"a hit-test that disagreed with the renderer would find nothing at all" —
but `grab_a_badge` scans cells with `badge_at` itself (`:305-313`), so it
finds whatever the hit-test believes, never what was drawn. Ticket 10's
NOTES ("the renderer and the hit-test are checked against each other") is
true of `badge_spans` and false of `badge_index_at`.

**Why it matters.** This is the milestone's signature fault, freshly minted
in the ticket that existed to close it. User impact is bounded — a drop opens
a menu titled `<source> → <target>` and then a preview, so a mis-grabbed badge
is visible before anything runs — but on a busy graph (the user works on
dependent team branches) a press on a badge picks up nothing or the branch
beside it.

**Fix.** Make the frame's view-finishing a function (`fn finished_view(session,
state, area) -> GraphView`) called by both `view_with_graphics` and
`badge_index_at`, so the hit-test cannot be handed a different view. Then
add the app-level agreement test: draw `view::view` into a `TestBackend` at
≥100 columns over a fixture with >8 lanes and two branches on one row
(Nerd icons too), and assert `badge_index_at(col, row)` names the badge whose
text occupies that cell. Fix the `name_and_drag.rs:293-296` comment either
way.

### M2. `answered()` reads *any* difference from idle as answered, and its comment says the opposite of what protects it

`crates/graft/src/update/tests.rs:3487-3492`:

```rust
fn answered(state, idle, name) -> bool {
    presses_for(name).into_iter().any(|press| outcome(state, press) != *idle)
}
```

The doc above it (`:3480-3486`) says a key consumed by the focused handler
"comes back with *fewer* commands than the inert key … 'Differs from inert'
catches it". It does not: fewer commands ≠ idle → `true` → **answered**, not
dead. The mutation went red (builder's evidence, 12 entries) because after
`settled()` (`:3448-3466`) the idle press in those states emits **no**
commands, so a consumed-and-dead `⏎` equals idle. Nothing asserts that:
`settled` compares state only, `nothing_happened` (`:3469-3478`) checks the
two inert keys agree, not that their command list is empty. Any state that
emits a steady ambient command on every event would make every
consumed-but-dead key on its bar read as answered, silently.

**Fix.** In `nothing_happened`, `assert!(idle.1.is_empty(), "…settled state
still emits {:?}")`, and rewrite the comment to say what actually holds:
after settling, "nothing happened" is `(same state, no commands)`, and a
dead key is one whose outcome is exactly that. If some context legitimately
cannot settle to zero commands, name it and mark the sweep blind there, the
way `blind` already does for the drag (`:3335-3341`).

### M3. The enumeration disclosure is rosier than the code

Ticket 31 NOTES: "a *new variant* cannot be missed; a new *field* on an
existing variant … can be." `KNOWN_GAPS.md:554` repeats it ("the compiler
forces a new *variant* into it"). The code disagrees with both:
`every_context()` is a literal array (`graft-ui/src/graph_screen/hints.rs:817`);
`marked_form` (`:859`) and `pane_focused_form` (`:887`) are exhaustive
matches, but a new variant is satisfied by `| NewVariant => None` and the
array never learns of it. The same holds for `screen_for` in
`update/tests.rs:3588`. The code's own doc is the honest one (`hints.rs`,
just above `every_context`: "writing the variant into the list is still a
human's job"). So the hole is: **a new variant can be missed too**, if the
builder answers the compile error with a `None` arm.

**Fix.** Correct the KNOWN_GAPS row and the ticket NOTES. To make it true
instead: have `every_context` *derive* its plain list from the exhaustive
match — e.g. a `fn forms(variant_tag) -> Vec<HintContext>` matched
exhaustively over a fieldless `HintKind` enum that `every_context` iterates
by listing `HintKind`'s variants once, in one place next to the enum. That
still leaves one hand-written list, but it is then a list of tags with no
fields to forget.

### M4. The converse direction is narrower than "both directions are covered"

Ticket 31 NOTES: "The two tests together cover both directions."
`every_planned_hint_is_still_unbound` (`update/tests.rs:3928-3960`) walks
`every_hint()` filtered to `HintState::Planned` and asserts none is in
`bound_actions()`. That covers *bound while the table says planned*. It does
not cover *bound and in no table at all*: a key bound in a handler and never
added to any `context_list` passes both sweeps, whether or not it is added
to `bound_actions()` (`keys.rs:723`, hand-written). Ticket 24's defect was
the Planned case, so the mutation asked for was answered honestly — but the
summary sentence claims the whole converse.

**Fix.** One more walk: every `(key, verb)` in `bound_actions()` appears
`Live` in at least one context's `whole_bar`, with a named exemption list for
keys that are deliberately never hinted (if any). Then the sentence is true.

### M6. The sweep varies the bar's width but never the state's

`update/tests.rs:3569` fixes every fixture at 160×48; the six widths
(`:3305`) only change what `hints_for` is asked to draw. So the bar drawn
for 40/80/100 columns is pressed into a side-by-side, non-Tab state. The
Tab layout (<100 columns) is exactly where ticket 29/31's defect lived, and
it is never the state under the keys. Nothing today is known to differ
there (the `<>` case is handled by `GraphView::detail_shown`), so this is
a coverage finding, not a behavioural one — but "at any width" in the
invariant is not what the test does.

**Fix.** Build the state at each swept width (`state.size = Size { columns,
rows }` inside the width loop) so the handlers see the layout the bar was
drawn for. If some widths cannot settle, say which.

## Minor

### m1. `can_start` does not ask `text_field_open()`

`crates/graft/src/update/drag.rs:146-156` lists eight conditions by hand
and omits the search prompt (`search_prompt`) and the focused banner
(`banner_focus`). With the search prompt open, a left press on a badge
starts a drag; the prompt then claims every key (`update/mod.rs:582-585`
routes to `search_key` before `key_event`), so `drag_key` never runs and the
footer reads `release drop on a row  esc cancel` while the user types.
Ticket 10 piece 4: "a drag cannot start while … a prompt … is open." Use
`state.text_field_open() || state.banner_focus || …` and keep the
overlay/menu/preview conditions.

### m2. A resize does not cancel a drag

Ticket 10 piece 4 lists "a resize" among the cancellations; `Event::Resize`
(`update/mod.rs:590-598`) does not touch `state.drag`. Harmless (the next
`Drag` event re-reads `over`), but it is a sixth undisclosed deviation — the
NOTES list five. Either clear `drag` there or add it to the NOTES.

### m3. "Over" ignores the column

`drag.rs:71` sets `over` from `graph_row_at(state, mouse.row)`, which takes
the row only (`geometry.rs:283`). Dragging across into the detail pane at a
graph row's height keeps that row as the target, and a release there opens
the drop menu. Ticket: "the working-tree row, header, footer, pane → None".
Check the column against `primary_pane_area` before accepting the row.

### m4. Caption whitespace run in the three new `detail` captures

`crates/graft/tests/it/hint_bar.rs:446` contains a 14-space run mid-sentence
("at 80 the              Detail tab owns the screen"), reproduced at line 10
of `docs/shots/m5-hints-detail-{80x24,120x40,160x48}.txt`. A string
continuation swallowed a newline but not its indentation. Textual; stands on
the capture alone.

### m5. Two doc references name tests that do not exist by that path

- `crates/graft/MAP.md:567` (`bound_actions` entry) still says
  `every_hinted_key_is_bound`, twice; ticket 31 renamed it.
- `crates/graft/src/view/hit.rs:10` cites
  `view::tests::badge_spans_match_the_drawn_cells`; the test is
  `graft_ui::graph_screen::tests::…` and, per M1, does not prove what the
  sentence says.

### m6. A refused `stash branch` preview loses the typed name

`update/name_prompt.rs::create` sets `state.name_prompt = None` before
`open_preview`; on `!opened` it restores `stash.shown` but not the prompt,
so a name typed while a write is running is gone and must be retyped. Keep
the prompt open (with the status line explaining) instead.

### m7. `border_row`'s cut-label branch has no direct test

`frame_box.rs::border_row` gained a second branch (`full > inner`: reserve
one blank cell before `right`). The sweep reaches it only where a title
happens to overflow at one of five widths. A one-line unit test with a
label longer than `width - 2` pins it regardless of which widget's title
grows.

### m8. `ContextMenu::selected_refusal` indexes unchecked

`graft-ui/src/context_menu.rs::selected_refusal` does
`self.items[self.cursor]`. Every constructor today guarantees at least one
item (`for_drop` is only reached with a non-empty `verbs`, `drop_menu`
returns `None` otherwise), so this is not reachable — but `.get(self.cursor)
.and_then(..)` costs nothing and removes the panic path from a widget crate.

## Questions

### Q1. Overlay behind the Detail tab: are the row's keys answered?

`view/frame.rs:415` draws the Detail tab's bar from
`pane_hint_context(state)` when an overlay (Map, journal, commit editor)
owns the primary tab. That is `PaneFocused { row: PlainRow, .. }` /
`PlainRow`, so the bar offers `c`, `m`, `r`, `b`, `t`, `y`, `x`, `/`, … with
the overlay behind the tab. The sweep never builds an overlay-plus-pane
state (`screen_for`, `update/tests.rs:3588`, has none). No line proves a key
is dead there; filed as a question: does the overlay's `shown_key` claim
those keys before the graph does, and if so, which bar should the Detail tab
draw?

### Q2. `1 first-parent` on the Detail-tab bar

`docs/shots/m5-hints-detail-80x24.txt` ends its bar with `1`
(`keys.rs:741`, `1 first-parent`). The sweep says it is answered, and it is
— it flips the graph's view while the pane owns the screen and the graph is
not visible. Same family as the `space fold` row in `KNOWN_GAPS.md` (M5/31):
answered, but acting on something the row does not show. Design question,
not a defect.
