## Minor

### 1. MAP.md says every reader goes through the shallow list; `reflog::first_parent_distance` does not
- `crates/graft-git/MAP.md:182` says "Every reader in the crate goes through this one list".
  `crates/graft-git/src/reflog.rs:108` walks `commit.parent_ids()` directly.
- On a clone made shallow after the fact (`git fetch --depth` over full history, or a hand-written `shallow`, as in
  32's own graph test), the boundary's parent object still exists. The distance then counts across the cut, where
  git's rule stops. On a fresh `--depth` clone the parent is missing, and the `NotFound` arm (`:103-105`) gives the
  same `None` git's rule would. **Unverified by test.**
- **Fix:** read the `ShallowList` once per call and stop at a listed id, or narrow the MAP line to "every history
  walk".

### 2. Four of the seven entry points that read `shallow` have no test for an unreadable file
- Tested: `Walk::all_refs`, `first_parent_merges`, `read_commit` (`shallow_history.rs:338-356`). Untested:
  `CommitTable::open` → `TableError::Shallow` (`table.rs:53`), `commit_graph::status` → `CommitGraphError::Shallow`
  (`commit_graph.rs:119-121`), `ahead_behind` (`divergence.rs:63`), and `first_parent_chain` (`read.rs:139`).
- **Why it matters:** rule 3. Replacing any of those `?` with `.unwrap_or_default()` stays green. `status` feeds
  `RepoStore::refresh` (`repos.rs:237`) and the commit-graph fact (`repository.rs:110`).
- **Fix:** extend `an_unreadable_shallow_file_fails_the_walk` with the four calls.

### 3. `escape_key`'s last rung can't do anything
- `crates/graft/src/update/keys.rs:553-558` calls `place::show_again`. Whenever `esc_goes_back` is true,
  `detail::keys::place_key` (`detail/keys.rs:84`) has already taken `Esc`: `pane_and_overlay_key` → `detail_key`
  (`keys.rs:280`) runs for every focus, and an overlay makes the predicate false. The comment at `:554-556` says as
  much.
- **Why it matters:** the rung reads as reachable. A reader tracing "why didn't the `G` withdraw run?" has to work out
  that it is dead. This is clever code where plain code would do (PROMPT.md 6.2).
- **Fix:** replace the call with a one-line comment that names `place_key` as where going back happens, or keep it and
  add a `debug_assert!(!esc_goes_back(next))`.

### 4. `ShallowList::read_in` has no caller of the kind its doc names
- `crates/graft-git/src/shallow.rs:34-36`: "for a caller holding only the common directory (a `gix::Repository`'s)".
  Its only caller is `read` (`:31`).
- **Fix:** fold it into `read`, or keep it and fix the doc. The spec named it, so this is a cleanup, not a defect.

### 5. The `^` "can't tell" state is reachable only from a hand-built answer
- `read_blame` answers `Some(came_from(..))` whenever `came_from` is set (`jobs/detail.rs:156-177`); a failed diff
  fails the whole job. So `answer.rs:139-143` and the fallback words at `answer.rs:177` are only reached by
  `a_came_from_answer_without_a_line_says_so`'s hand-made `line: None`.
- This is built as ruled (Minor 1). But the user can never see the words, and the type says the job can produce them.
- **Fix:** none needed now. If 21 reuses `BlameAnswer`, make the came-from line required when it is asked for (an enum),
  and drop the arm.

### Q1. Does a `⏎` landing still seeking finish under the place after `Esc` goes back?
`show_again` (`place/trail.rs:80-86`) sets `trail.shown` and leaves `state.line_landing` alone. `leave` does drop it
(`trail.rs:46`). `detail::landing::advance` (`landing.rs:141-166`) runs after every event and has no trail check. So
after `B ⏎ Esc` on a commit the walk has not reached yet, the landing may go on to select the commit, open the pane,
or say "missed" on the status line while blame is on screen. Leaving blame then restores the origin spot. 20i's NOTES
raise this as an open question, and there is no KNOWN_GAPS row. Not observed. It needs a test: `⏎` onto an unloaded
commit, `Esc`, then deliver the rows.
