## Major

1. **The graph bar leads `esc back to blame` while `Esc` closes the pane instead** (reproduced).
   - **Where:** `view/rows.rs:410` wraps every row context in `BackToBlame` whenever the trail is hidden. With the graph
     focused and the pane shown, `Esc` reaches `detail_key` first:
     - `update/detail/keys.rs:67` shows the trail only when the pane is focused;
     - `:126` (`KeyCode::Escape if detail.shown => detail.close()`) closes the pane.
   - **Seen:** scratch test, `⏎` landed, `line_landing` cleared, focus on the graph, pane shown. The bar's first hint
     is `("esc", "back to blame")`. After `Esc`: place on screen `false`, pane shown `false`. I did not observe a
     second `Esc`. By the code it reaches `escape_key`'s last rung (`update/keys.rs:555`) and goes back.
   - **The ticked tests miss it:**
     - `graph_bar_leads_esc_back_to_blame_while_hidden` (`place/tests.rs:1388`) pins the bar with the focus on the graph
       after `⏎` from `pane_at`, whose pane is shown, and never presses the key. I did not check whether the pane is
       still shown in that test's state. My scratch test set it shown explicitly.
     - `esc_on_the_graph_closes_search_before_returning_to_blame` closes the pane in its setup to step around it
       (`:861`).
   - **Why it matters:**
     - The bar and the key disagree, the m5/31 class of defect.
     - Keymap §2.1 (`02-keymap.md:80-82`) promises `Esc` on the graph returns "once the graph's own menu, box, prompt,
       search, Focus or Explain is closed". The pane is not on that list.
     - `commit-back-to-blame` becomes 2 after one `Tab`.
   - **Fix:** a spec call, through the conductor. Either:
     - `Esc` on the graph with a hidden trail shows it before closing the pane (the keymap's reading); or
     - the bar leads with `esc close` there, and `esc back to blame` only where `Esc` goes back.

     Either way, add a test that presses `Esc` in the bar test's state.
2. **Nothing tests that a write ends the trail through `update`.**
   - **Where:** deleting `place::after_commands(&mut next, &mut commands);` (`update/mod.rs:140`) leaves all 60 place
     tests green (mutation M3). `a_write_clears_the_trail` (`:1152`), `is_write_covers_every_operation_launch` (`:877`)
     and `a_write_with_a_base_aside_pins_it_again` (`:1043`) all call `after_commands` directly.
   - **Why it matters:**
     - The spec says "after `update` returns commands, any `is_write` command clears the trail" (20:83).
     - This one line is what keeps a trail from pointing at lines a write moved.
     - It is also what re-pins a set-aside base after a write. A refactor of `update` could drop it silently.
   - **Fix:** one test through `update`: trail hidden, base set aside, `u` on the graph. Assert the trail is gone and the
     base is pinned.
3. **The blame job has never run against git.**
   - **Where:** `jobs/detail.rs:145-186` (`read_blame`) has no test, and all 60 place tests inject its answer. Untested:
     - `^`'s diff read: a hand-built `FileEntry` (`FileStatus::Modified`, `old_path` only on a rename), `context: 0`,
       `against: None`;
     - the `BlameError` → `BlameFailure` mapping (`Binary`, `Untracked`, and `Shallow` shown as `Failed`).
   - **Why it matters:**
     - `^` landing "where the line came from" is the journey's promise. Today it rests on `came_from`'s unit tests and a
       faked `line: Some(9)` (`caret_lands_where_the_line_came_from`, `:643`).
     - 20f's `blame-line-before` walk will cover one plain file. It will not cover a rename or a refusal.
   - **Fix:** a `tests/it` test on the session fixture. `^` on a line of a renamed file must answer git's own
     `blame --porcelain` `previous` line. A binary and an untracked path must map to their refusals.
4. **New files over 400 lines** (PROMPT.md 6.2):
   - `crates/graft/src/update/place.rs` is 600 lines;
   - `place/keys.rs` is 449;
   - `place/tests.rs` is 1414 (753 from 20e, 661 from 20g).

   Precedent: M6/07 and M6/11+12 track the same thing. **Fix:**
   - Move the job's answer (`blame_arrived`, `BlameAnswer`/`BlameFailure`/requests) to `place/answer.rs`.
   - Move the trail's life (`trail_back`, `leave`, `after_commands`, `end_for_compare`, `show_again`) to
     `place/trail.rs`.
   - Move `BlameState`'s methods out of `keys.rs`.
   - Split the tests by box: open, navigation, pinned base, keys and states, hints.

## Minor

1. **`^` then `w` before the parent's blame arrives puts the cursor on line 1** (reproduced).
   - `rerun` keeps `Want::CameFrom` (`place/keys.rs:162-166`) but asks with `came_from: None` (`:182`).
   - The answer's `line` is then `None`, and `place.rs:559` (`answer.line.unwrap_or(1)`) turns that into line 1 with no
     word. That is rule 3: a fallback standing in for a missing answer.
   - **Fix:** keep the `CameFromRequest` in `BlameLoad::Reading` and resend it. Also make a `CameFrom` answer without a
     line a failure, not line 1.
2. **`came_from` is off by the deletion's size for the line just before a pure-deletion hunk** (reproduced).
   - git writes a deletion of old 5–6 as `@@ -5,2 +4,0 @@`: a zero-count `new_start` is the line *before*.
     `came_from(&[hunk(5,2,4,0)], 4)` returns 6; old line 4 is right.
   - The code is `from.rs:128-137`: `4 < new_start` is false, `4 < end` is false, then it shifts by 2.
   - It is reached only for a line outside every hunk of the commit's diff (rare with `-w`; the ignore-revs list can
     cause it).
   - **Fix:** with `new_lines == 0`, treat `new_line <= new_start` as before the hunk. Add the case to the unit tests.
3. **`B` answers in the changes pane, but that pane's bar never offers `B blame`.**
   - `view/rows.rs:673` returns `ChangesPane` with no blamable flag. Only `PaneFocused` gets one (`:718`).
   - Design note B1 names the changes pane as a `B` source, and UX heuristic 1 (visibility) applies. The 20e NOTES list
     it as a deviation, but no row tracks it.
   - **Fix:** a `blamable` field on `ChangesPane`, read from `place::blamable`.
4. **`B` on the changes pane is tested with the file list only through `blame_from`.**
   - `b_on_the_changes_pane_blames_the_working_tree` and `…removed_line_blames_head` put the cursor in the diff
     (`changes_at`, focus `Diff`).
   - No test presses `B` with the changes pane's file list focused, which is the design's "a file" case.
   - **Fix:** one test on a file row.
5. **git's failure words reach the blame body unsanitised.**
   - `BlameState::view` passes `BlameLoad::Failed(words)` straight through (`place/keys.rs:431`), and graft-ui draws it
     with `put` (`blame.rs:240-243`). The words carry git's stderr, which names the path.
   - Other views sanitise failure words at this boundary (`view/finish.rs:32`, `view/journal.rs:27`).
   - ratatui 0.30's `set_stringn` drops control-character graphemes, so no escape reaches the terminal. `sanitize_line`
     also neutralises `Cf` (bidi) characters, which that filter does not.
   - **Fix:** `sanitize_line` in `view`.
6. **The Navigation tick contradicts itself.** `20-blame-place.md:136-141` says 20g added "the rename half of
   `enter_lands_on_the_commit_with_the_diff_at_this_line`". The same parenthesis also says "the rename half of
   `enter_lands_…` not covered". The test covers it (`place/tests.rs:731-749`). **Fix:** drop the stale clause.
7. **`i_toggles_ignore_revs_and_the_line_says_which` asserts only the option** (`place/tests.rs:1227-1233`). The line's
   words are never checked.
   - While the re-read runs, `ignore_line()` is `None` (`keys.rs:405-408`), so the ignore line and the bar's `i` vanish
     until git answers.
   - **Fix:** assert the line after the answer. Decide whether the line should last through a re-read.
8. **Click geometry is duplicated, and nothing ties the two copies together.**
   - `place/keys.rs:300-319` re-derives graft-ui's `body_area` in plain `u16`s, because `update` may not name ratatui.
     graft-ui's `blame_row_at` is unused by the app. The 20e NOTES record this as a deviation.
   - **Fix:** a `view` test that clicks each drawn body row. The cursor must land on the row drawn with `▸`.
9. **ARCHITECTURE.md's "where to change what" list has no entry for blame or places** (`ARCHITECTURE.md:80-95`).
   - **Fix:** add a bullet for `ui::blame`, `app::update::place`, `app::view::frame::overlays::draw_place`, and the job
     in `app::jobs::detail`.

Also noted, not counted: `blame_arrived`'s refusal arm maps an unreachable `BlameFailure::Failed(_)` to
`NoBlame::Untracked` (`place.rs:572-575`). Plain code would use two arms. Fold this into Major 4's split.
