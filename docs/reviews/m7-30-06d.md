## Major

### Major 1: on the fallback, a staged new file edited on (`AM`) loses its staged content, and the line doesn't name it
- **Where:** `crates/graft-ops/src/apply/set_aside/put_back.rs:178` (`staging_lost` leaves out every `A` path), and the
  unit test that pins that rule, `put_back.rs:259-267`.
- **What:** a plain `stash apply` re-adds a staged new file **from the working tree**. If he staged `n.txt` at v1 and
  then edited it to v2, v1 is gone from both the index and the tree after the fallback. Because the rule treats `A` as
  "comes back staged", the words name only the other files. Reproduced through Graft's own `apply` (a throwaway
  test in the mutation worktree; P3's fixture plus `n.txt` `AM`): `unread = [StagingNotKept { paths: ["f.txt"] }]`,
  status ` M f.txt` / `A  n.txt`, `:n.txt` = `v2`, and the line reads
  `your edits are back · staging not kept: f.txt · u undoes it, staging included`. The same happens in plain git (my
  probe: `AM n.txt` → `A  n.txt`, index v2).
- **Why it matters:** this is the silent loss the ticket was written to end (30 Decided 1, second bullet: "content that
  exists only in the index is lost … and nothing tells him"). v1 survives only in the entry's backup. `u` right away
  brings it back. After another write it takes the journal browser, and nothing on screen points him there. KNOWN_GAPS
  M6/83 lists `AM` as unverified; it is now verified broken on this path.
- **Fix:** name an `A` path too when its staged blob differs from the stash's working-tree blob, i.e. `S^2:path` ≠
  `S:path`. For example, one `diff-tree -r --no-renames -z S^2 S` restricted to the added paths, or `ls-tree` both.
  Add the `AM` row to T5, red first. The words stay the same: a staged new file whose staged content went is "staging
  not kept".

## Questions (no line proves a defect)

1. **A kill mid-put-back.** The fallback adds a new window: after the plain apply lands (`put_back.rs:70`) and before
   the drop (`returned.rs:153`), the edits are in the tree without their staging **and** `S` is listed. On relaunch,
   the interrupted line names `edits in stash@{n}` (the pattern pinned at
   `crates/graft/src/update/undo/tests/set_aside.rs:52`), and the lost staging is named nowhere. `u` should still
   restore the backup. I did not verify it: no test kills the process between the two applies or between an apply and
   the drop. `the_rm_cached_bytes_are_never_only_on_disk` stops only before steps 4–6, and a put-back never stops.
   Is a kill test wanted, and should the interrupted line say the edits may already be back?
2. **Journal failure after a fallback.** `set_aside.rs:266-273` puts the full `StagingNotKept` words, `· u undoes it,
   staging included`, into `ApplyError::Journal.kept`. With no outcome line written, the held entry is presumably
   still `Pending`, which is not in force, so `u` would undo the entry before it rather than this one. I did not
   check what the app does with `u` after a `Journal` failure. If `u` is blocked or misdirected there, the words
   should drop their key half.
