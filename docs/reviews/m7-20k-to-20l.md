## Major

**1. 12f: `until_promoted_window_for` has no bound. If promotion regresses, the heavy test hangs instead of failing.**
`crates/graft/tests/it/heavy.rs:336-360`, doc at `:330-331`.
- *What:* the helper loops on blocking `told.recv()` (`:342`). Its doc says it is "bounded as `until_window_for` is:
  by the stream ending". The stream does not end while the test holds `asks`:
  - `asks` is alive for the whole `thread::scope`.
  - Once caught up, the worker parks in `requests.recv()` (`history/serve.rs:146`).
  - So if the promoted window never comes, `recv` blocks forever, and the panic that names the unpromoted count
    (`:355-357`) is unreachable in that case.
- *Why it matters:* the ticket asked for a helper "bounded by the same timeout", and for a promotion that never comes
  to fail as `blocked: promotion never swaps`. It also breaks PROMPT.md 7.1's no-hangs rule. The failure this test
  exists to catch (Part C's swap regressing) is exactly the one that now hangs the heavy tier. `until_window_for`
  (`:316`) has the same flaw, so the builder copied a real gap rather than creating one. The doc comment still claims
  a bound that isn't there.
- *Fix:* `told.recv_timeout(PATIENCE)` in both helpers, or `crate::deadline::Deadline` as 33b put into the other
  loops. Drop the `asks` sender before any wait whose end relies on the stream closing. Correct the doc.

**2. 20k: `HintContext::Blame { read }` means the opposite of what it reads as, and misses `Failed`.**
`crates/graft-ui/src/graph_screen/hints/context.rs:229`, `crates/graft/src/view/rows.rs:598`,
`hints/lists.rs:147-163`.
- *What:*
  - `read: true` means "a read is in flight", i.e. *not yet read*. `Blame { read: true, .. }` in a test or match arm
    reads as "the blame has been read". PROMPT.md 6.2 (names) applies.
  - The flag also encodes the wrong fact. The keys it hides (`⏎`, `^`) need *lines*: `place/keys.rs:219` and `:273`
    return on anything but `BlameLoad::Ready`. `Failed` has no lines either but draws both. That is Question 1's
    other half, confirmed, below.
- *Why it matters:* a flag named for the mechanism rather than the fact led straight to the second dead-key state.
  The seam's name came from 20i's ticket, so this is not the builder's invention, but it ships in a public graft-ui
  variant.
- *Fix:* one flag that states the fact, `lines: bool` (`matches!(body, BlameLoad::Ready { .. })`), set at
  `rows.rs:598`. `blame_bar` then drops `⏎ ^ n N` when `!lines`. Add a `Failed` place to `place_reading`'s sweep
  (`answer.rs:142` makes one: `^` on a line with no parent). This also closes gap M7/20k-q2.

**4. 16a: `stashes` is settable two ways.** `crates/graft-graph/src/inclusion.rs:66`, `:74-83`.

**5. 14a: `only_in_stash` fails outright on an unborn `HEAD`.** `crates/graft-git/src/history_reads/compare.rs:174`.
- *What:* `^HEAD` is always fed to `rev-list --stdin`.
- *Checked:* in a scratch repo with a stash, `git checkout --orphan fresh`, then the same `rev-list` command gives
  `fatal: bad revision '^HEAD'` and exit 128 (git 2.54). So the whole read is `Err` and 16's marking gets nothing.
  `unreached.rs:101` has the same line.
- *Fix:* omit `^HEAD` when `HEAD` does not resolve (the caller knows `head_state`), or use `--ignore-missing`, as
  `unreached`'s first spawn does, and cover it with one test on an orphan branch.

**6. 14a: the attribution tests never give two entries different bases.** `crates/graft-git/tests/it/compare_and_stash.rs:192-262`.
- *What:* every case has one base commit (`A`), apart from the skip case, which gives `(A, 1)`. Nothing checks that
  `stash@{0}` and `stash@{1}` on two different rebased-away bases come back as `[(B,0), (A,1)]`, in that order, with
  `claim`'s early `continue` (`compare.rs:220`) not starving entry 1.
  - The stop tests only raise `Stop` before the first spawn (`:125`), never between the `cat-file` and the
    `rev-list`.
- *Fix:* add one two-base test. For the stop, use one `Stop` that raises after its first check.
