## Major

### M1 (20b) — `show_line(WorkingTree, …)` lands in the **staged** diff for a file with staged and unstaged edits, so blame's `⏎` on an uncommitted line puts the cursor on the wrong line

- **Where:**
  - `crates/graft/src/update/detail/landing.rs:212` (`select`) takes the **first visible row** whose entry path matches.
  - The changes pane lists `Unmerged`, then `Staged`, then `Unstaged` (`crates/graft/src/jobs/detail.rs:380-393`). A
    partly staged file therefore matches its `Staged` row first.
  - That row's diff is index against `HEAD` (`jobs/detail.rs:96`, `DiffSpec::Staged`), so its `New` side counts lines
    in the **index**.
  - The only `WorkingTree` caller passes a **disk** line number: `crates/graft/src/update/place/keys.rs:226`
    (`final_line` of a blame of the file on disk), sent as `Side::New` at `:245-252`.
  - `place` then uses `line_row` (`cursor.rs`), which finds the nearest row at or before that number in the wrong
    diff.
- **Why it matters:** this is the `blame-line-to-commit` journey on a daily case: he stages part of a file, blames it,
  and presses `⏎` on a line he hasn't committed. The line may be an unstaged edit, which is absent from the staged
  diff. Or the unstaged edits may shift the numbering. Either way the cursor lands somewhere plausible but wrong, and
  nothing says so. 20's design considered this file shape for `B` (`20-blame-place.md:44`) but not for `⏎`'s landing.
  **Not reproduced by running the app.** The claim rests on the four lines above.
- **Fix:** for `DetailSpec::WorkingTree`, prefer the `Unstaged` row when the path has one. Its `New` side is the disk,
  which is what the working-tree blame numbers. Fall back to `Staged` or `Unmerged` otherwise. Alternatively, give
  `show_line` an optional section, which is a signature change through the conductor. Test: a partly staged file where
  the unstaged edit adds a line above the target. The landing must be on the disk line.

## Minor

### m1 (20a) — `a_repeated_filename_keeps_the_commits_path` cannot fail on the rule it names

- **Where:** `crates/graft-git/src/blame/tests.rs:317-339`. The second entry of the same commit repeats
  `filename a.rs`, the same value as the first. A parser that kept the **last** `filename` passes this test just as
  well as one that keeps the first.
- **Why it matters:** the test's name and its tick claim "the first stays", and the test does not tell first from
  last. Behaviour is fine today (`record_commit` returns early once the id is known).
- **Fix:** make the repeat `filename b.rs` and assert `a.rs`.

  module doc names as a future caller, would reach it.
- **Fix:** search `files.rows` for the entry. If it is hidden, unfold its collapsed ancestors (`toggle_dir`), then
  select it.
