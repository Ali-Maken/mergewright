## Major

### M1. Journey 15 is refused whenever it arises: an undo that replaced his edit always leaves the file dirty

- **Where:**
  - `crates/graft-ops/src/operation/recover.rs:191-208`: a `Files` put-back refuses with `UnsavedEditsTo` when the
    path is staged, unstaged or untracked.
  - Fixture `crates/graft-fixtures/src/lost_work.rs:16-17` and `:255-259`.
  - The walk: `crates/graft/tests/it/m7_walk/journal.rs:329-370`.
- **What:**
  - A lost edit is made by an undo that wrote over his newer edit. The fixture does exactly that: he discards
    `DISCARDED_EDIT`, writes `LOST_EDIT`, and a forced undo puts `DISCARDED_EDIT` back.
  - So after that undo the file holds the undo's restored content, which differs from `HEAD`. In the scenario that
    creates a lost edit, the file is dirty by construction, so `⏎` on the lost-edit row is refused.
  - The refusal then offers `c commits or S stashes them first` (`crates/graft/tests/it/journal_screen.rs:65-67`; walk `:362`). Both keys would
    keep the content he had discarded.
  - The builder filed this as a fixture question (NOTES 24-b). The lines above say it is the journey, not the
    fixture.
- **Why it matters:** nothing is lost, because the backup holds it. But J cannot give it back from inside the app, and
  journey 15's count, `J n ⏎ y` = 4, is unreachable in the journey's own situation. The walk proves only a route that starts after he leaves the app.
- **Fix:** planner's ruling. Two options:
  - The Files put-back sets the current content aside and names it in the box. `FilesEffect::Changes.set_aside`
    already has words: `1 unsaved file set aside, put back after`.
  - Or the refusal offers an in-app next step that fits: discard the undo's restored content, with a backup.
  - Then re-count the journey against the fence. Do not change the fixture to make the file clean: the dirty file
    is the real case.

### M4. `u` in J and `⏎` on the `← u` row now disagree in two cases; "launched" is inferred from `commands.len()`

- **Where:**
  - `crates/graft/src/update/keys.rs:142-148`: `undo_key_anywhere` closes J iff `commands.len()` grew.
  - `crates/graft/src/update/journal.rs:809-810`: `⏎` on `← u` closes J **before** `undo_key`.
  - `crates/graft/src/update/undo.rs:42-44`: `u` after a push opens the confirm box and returns no command.
  - `crates/graft/src/update/undo.rs:71`: "Undo locally" launches without closing J.
  - `crates/graft/src/update/undo.rs:255-257`: an in-progress refusal pushes nothing.
- **What:**
  1. A refusal: `u` keeps J up with the refusal on J's status row, as the ruling asks. `⏎` on the same row closes J
     first, so its refusal lands on the graph's bar.
  2. After a push: `u` in J opens the undo-after-push box with J still up. Choosing `Undo locally` runs the undo and J
     **stays open**. `⏎` closes J first, so the box and the landing are on the graph.
- **The V8 ruling and the deviation:**
  - Keeping J up on a refusal is sound: it is the ruling's own refusal clause, and closing first would drop the words
    where he can't see them.
  - It is half applied. The ruling's premise, that `u` lands as `⏎` does, no longer holds on either path above.
  - "Did it launch?" is read off a `Vec` length. That is a proxy: any future command pushed on a refusal path, a
    `CancelJob` for example, would close J under its own refusal.
- **Why it matters:** this is the same inconsistency the m6 usability walk filed ("same key, same meaning";
  ux-principles H4). And the proxy is clever code where plain code would do (6.2).
- **Fix:** one function for both keys, e.g. `journal::undo_from_j(state, commands, redo)`. `undo::undo_key` returns
  an enum, `Launched | Asked(box) | Refused`. J closes on `Launched`, and on `Asked` it closes when the box's choice
  launches. `enter_graft` calls the same function.
