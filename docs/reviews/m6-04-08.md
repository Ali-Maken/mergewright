## g08 against the M3 promise ("you cannot lose work")

**Where no work is lost:**
- **Undo of anything touching an unmerged index, with no operation live.** This covers a conflicted stash pop, a resolution of it, and redo of either. Every such entry now records `IndexState::Unmerged`. `RestoreIndex` puts the stages back exactly: a mode-0 record first (`restore/steps.rs:179-200`, `index_info_records`), and `ls-files -u` is compared byte for byte in the tests.
- **A folded step inside a Graft-begun operation.** Each one chains a backup before it runs (`apply/resume.rs:89-98`), and `resume` does the same before `--continue`, `--skip` and `--abort`. The after-snapshot parents the chain tip, so every commit in the chain stays reachable.
- **`d` after `⏎`.** It restores the stages *after* the backup, so the resolution being started over from is kept.

**The one path that still loses work:** a whole-file take or a `d` inside an operation **begun in the shell** (Major M1). No backup of any kind is taken there.

## Major

### M1 (g08). A whole-file take or `d` inside an operation begun in the shell takes no backup, and nothing records that gap
**Holds at HEAD: yes.**

**Where:**
- `crates/graft-ops/src/apply/resume.rs:89-98`:
  ```rust
  let step_backup = match &span {
      Some(entry) if touches.index || touches.worktree => {
          snapshot::chain_backup(ctx, entry).map_err(as_apply_error)?
      }
      // No entry of Graft's to chain onto (an operation begun in the
      // shell), or a step that writes neither: nothing to keep.
      _ => None,
  };
  ```
- `live_entry` (`resume.rs`, `pub(super) fn live_entry`) returns `None` for any merge, rebase, cherry-pick or revert that Graft did not start.

**What's wrong:** the g03 review's M2 data-loss path is closed only for operations Graft began. Say the user hand-edits a `deleted by them` file in `$EDITOR`, then takes theirs. That runs `git rm --quiet`: no confirm, no journal line, and now no chain commit either. The edit is gone. The same applies to `checkout --ours|--theirs` over a hand-edited `UD`/`DU`/`AU`/`UA` file, and to `d` (`checkout --merge`) over hand edits. `d` at least sits behind a confirm box.

**Why it matters:**
- KNOWN_GAPS already calls a merge begun in the shell ("a `git pull` that conflicted") "the user's likely daily case" (row "A merge begun in the shell … cannot be finished in the app").
- M3's promise is "you cannot lose work", and this is a path where the user loses it with no way back.
- The m6-05 review raised it (`docs/reviews/m6-05.md:138`: "in a shell-begun merge, a whole-file `t` or a `d` takes **no** backup … nothing on the app side names it"). There is still no KNOWN_GAPS row: grepping for "backup" and "begun in the shell" finds only the row about finishing the merge.

**Fix (the cause):** when `span` is `None` and the step touches the worktree, keep a standalone backup anyway. `snapshot::take` under a fresh `refs/graft/backup/<wt>/<ulid>` needs no journal line and keeps the bytes reachable. Recovery UI can come later. Alternatively, refuse a whole-file take on a shell-begun operation when the working-tree bytes differ from every stage's blob, and say so in words. Until either lands, file the row as **broken**.

### M2 (g04). `⏎` and a block take can be in flight together on the same file
**Holds at HEAD: yes.**

**Where:**
- `crates/graft/src/update/resolver.rs:291-326` (`mark_resolved`) checks `mark_resolved_refusal` and `state.operating`, but **not** `open.job`. So it launches `Stage` while a take on the same file is still in flight.
- `crates/graft/src/update/resolver/take.rs:48-68` (`take_side`) checks `busy_words()` (i.e. `open.job`) and `base_job`, but **not** `open.staging` or `state.operating`. So it queues a `TakeSide` while `⏎`'s `git add` is running.
- The pool runs jobs on several workers (`jobs/runner.rs:128-138`), so the two jobs run concurrently.

**The sequence (reasoned from those lines, not observed):**
1. Every block is taken. The user presses `t` on one block to change their mind; a re-take replaces the earlier take.
2. The user presses `⏎` before that take lands. Or: `⏎` first, then `t` before the stage's `git add` runs.
3. If `git add` reads the file before the take's rename, the index holds the old resolution and the working tree the new one.
4. `resolved_advance` moves on (`answers.rs:216-253`), and the late `Taken` answer is dropped because its id no longer matches (`answers.rs:116`).
5. The status line reads `all conflicts resolved · c continue`, and `c` commits content the resolver never showed as final.

Nothing is lost: the working tree holds the last choice. But the commit may differ from it silently.

**Why it matters:** this is the same class as m6-05's Majors 2 and 3 (two writers racing on one document with nothing serialising them). The window is narrow, but nothing closes it.

**Fix:**
- In `mark_resolved`, refuse with `open.busy_words()` when `open.job.is_some()`.
- In `take_side`, refuse with `a write is already running` while `open.staging.is_some() || state.operating.is_some()`.
- Add two tests: `o` then `⏎` before pumping, and `⏎` then `o` before pumping. Each should assert the refusal and that at most one command was queued.

## Minor

### m1 (g08). `backup_chain` recognises a backup commit only by a top-level tree entry named `index` or `unmerged`
**Holds at HEAD: yes. Latent:** `d` after `⏎` has no entry point in the app (KNOWN_GAPS "`d` after `⏎` has no entry point").

- `recorded_index_state` (`snapshot.rs:289-303`) returns `Some(Merged)` for **any** commit whose root tree has an entry named `index`, whatever its type.
- `backup_chain` (`snapshot.rs:327-332`) keeps walking first parents for as long as it gets `Some`.
- The pre-operation snapshot's first parent is a **user** commit (`apply.rs:951-956`: pins, then anchors).

So in a repository whose history has a top-level `index/` directory or `index` file, the walk runs down the user's entire first-parent history, two `git` spawns per commit. It returns only `Merged` states that `stage_source` then skips. The stop token still works, so it can be cancelled.

**Fix:** also require the commit to be Graft's. Its message starts `graft <ulid> ` (`commit_trees`, :500), or check the tree holds exactly `{index|unmerged, worktree}`. Add a test with a user commit that has `index/` at the root.

### m2 (g08). `stage_source`'s journal arm will restore any in-force entry's stages, however old, and is untested
**Holds at HEAD: yes. Latent,** for the same reason as m1.

- `check_restart` (`operation/conflict.rs:238-246`) admits **any** path the status does not call unmerged. That includes a clean path, and a path absent from the status.
- `journal_states` (`apply.rs:541-552`) then offers every in-force entry's `index_after` and `index_before`, newest first, with no bound.

Suppose a path was conflicted in some old stash pop and is clean now. A restart on it would put that old conflict's stages back and write markers over the current file. `u` would recover it, since the entry has a backup.

The builder's NOTES say this arm "has no integration test of its own reaching `Backup` … a reading, not an observation". That item is not in KNOWN_GAPS.

**Fix:**
- Bound the walk to the conflict the user is actually in. With nothing live, stop at the newest entry whose `index_after` is `Merged`; that is the end of the conflicted stretch.
- File the untested arm as **unverified**.

### m3 (g08). Two error mappings discard the real error
**Holds at HEAD: yes.**

- **`seal_after`, `apply.rs:1101-1104`:** `facts::read_refs(…).ok()…unwrap_or(before)`. The comment says the fallback "is the case the `Unsealed` arm below reports". It isn't: `Unsealed` (:1122-1131) reports only a failed `commit_trees` or `move_backup_ref`. If the read fails and the move succeeds, any chain is orphaned and nobody is told. The window is small today, because `close_resume` read the same ref with `?` just before. Rule 3 still applies. Fix: return `AfterState::Refs` or `Unsealed` on the read error, or pass the tip in from the caller, which has already read it.
- **`chain_states`, `apply.rs:525-533`:** `_ => FactsError::Stopped`, with a comment that `live_entry`'s only other failure is the stop. True today, but a new failure variant in `live_entry` would be reported as a cancel. Fix: match `ApplyError::Stopped` explicitly and map the rest to a real error.

### m5 (g08). A chained backup takes a full snapshot on every folded step; the cost is unmeasured
**Holds at HEAD: yes. Filed as a question**, because the cost has not been measured.

`chain_backup` → `both_trees` (`snapshot.rs:209-218`) runs `add -A` over an index copy on every folded `⏎`, whole-file `o`/`t`, `d` and resume. The copy has no entries for untracked, non-ignored files, so `add -A` presumably reads and hashes each of them again on every step. With a large untracked artefact, that is a full re-read per resolved file. The 15 ms / 5,000 files figure in MAP §snapshot is for tracked files with a warm stat cache. The worktree side of a chained step was never measured.

**Fix:** measure one folded step on a tree with a 1 GB untracked file, via a `docs/perf/` script. Decide from the result.
