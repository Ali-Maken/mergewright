## Major

### 1. The relaunch notice keeps launch-time words after the stash list changes: it says "a copy stays in stash@{0}" after that copy is gone (30c)

- **Where:** `crates/graft/src/update/undo.rs:718-727`. `interrupted_words` returns `edits_clause(*at)` from
  `AppState::interrupted_edits`, a fact read once at launch and kept until `J`. It never checks that the stash is still
  listed, or still at index `n`. The older branch just below it (`:732-745`) does re-read `state.refs.stashes()` on
  every draw.
- **Observed** (probe, reverted), in K4's state (killed before the drop, relaunched):
  1. At 120, the footer reads `… your edits are back · a copy stays in stash@{0} · J to inspect`.
  2. In the shell, `git stash drop`; the stash list is now empty.
  3. `Ctrl+R`, pumped until `state.refs` lists no stash.
  4. The footer **still reads `… a copy stays in stash@{0} · J to inspect`**.
- **Why it matters:**
  - This is the one line whose job is to say where his edits are, and it states a fact about the repository that is
    no longer true. Dropping the copy is the obvious next step once the edits are back.
  - The `Stash { n }` form (`your edits are in stash@{n} · S p puts them back`) goes stale the same way after `S p`.
  - **Unverified, reasoning only:** after he stashes something else, `stash@{0}` would name the wrong stash. That
    follows from the same line. I did not probe which stash `S p` then acts on.
  - It also inverts ADR-0045 §5's point: no guessed words. Recovery reads the fact, but the words outlive it.
- **Fix:**
  - Keep recovery's *kind* (`Stash` vs `Back`), but take `n` from `state.refs.stashes()` on every draw, looking up
    `entry.put_back.stash` as the fallback branch does.
  - When the stash is no longer listed, drop the clause. That is the same rule as today's
    ` · edits in stash@{n}` branch.
  - Add a unit test beside `the_notice_words_where_recovery_found_the_edits`: `interrupted_edits` holds
    `Back { copy: Some(0) }`, refs list no stash, and the notice has no `stash@`.
  - The K4 walk could add a `git stash drop` + `Ctrl+R` step.

### 2. 17: the refusal says "git can't" when git was never asked

- **Where:** `crates/graft/src/update/resolver/restart.rs:155` words every `StartOver::Cannot` as

  `could not check: …` when Graft's own reads failed (`graft/src/jobs/conflict.rs:269-271`).

  disclosed it (17 NOTES: "ops doesn't use resolve-undo"). Git's `checkout -m` may well be able to recreate the
  conflict from resolve-undo. The line blames git for a limit that is Graft's.
- **Fix:** `can't bring back the conflict in <file>: <reason>`. Or actually ask git, and word its refusal, as 17's
  Decided bullet 4 intended.

## Question

### Q1. 03-a: a pull that changes nothing still moves the cursor to `HEAD`. Wanted?

- **Where:** `operate.rs:980` takes `lands_on_head` from the launch's `moves_head()`. `Pull` is always true
  (`graft-ops/src/operation.rs:1223`). `landed` (`operate.rs:959`) lands on every `Done` and `StagingNotKept`, whether
  `HEAD` moved or not.
- **The case:** a daily `p` that answers "already up to date" jumps the cursor off the row he was reading.
- **What the spec says:** UX §3.1 says "land on the result", and with no result there is nothing to land on. The spec
  doesn't say which it wants, so this is a question, not a defect.
- **If it is unwanted:** land only when the refreshed `HEAD` differs from the launch's.
