    (`tests.rs:442-455`). They can only agree.

## Major

### 1. The heavy-feature clippy gate is red: `deadline.rs` is loaded as two modules (33)

- **Where:**
  - `crates/graft/tests/it/app_harness.rs:24-25`: `#[path = "deadline.rs"] mod deadline;`
  - `crates/graft/tests/it/budget_run.rs:36-37`: the same.
  - `budget_run` is compiled into `it` only under `heavy-tests` (`tests/it/main.rs:12-13`).
- **What's wrong:** `cargo clippy --all-targets --features heavy-tests -- -D warnings` fails with
  `clippy::duplicate_mod`. That is the review gate KNOWN_GAPS names under "The heavy code is not in the standard
  clippy gate", so the standard gates didn't show it.
- **What I checked:** I added a throwaway `#[allow]` on the second module (reverted). The heavy clippy run was then
  clean, so nothing else is hidden behind this error.
- **Why it matters:** a red gate blocks every later review's heavy-lint check. Two copies of `Deadline` also means two
  types in one binary.
- **Fix:**
  1. Declare `mod deadline;` once in `tests/it/main.rs`.
  2. In `budget_run.rs`, use `crate::deadline::{DEADLINE, Deadline}`.
  3. Give the `budgets` example its own root-level `#[path = "../tests/it/deadline.rs"] mod deadline;`, so that
     `crate::deadline` resolves in both crates.

  Alternatively, keep the `#[path]` in `budget_run.rs` only, and have `app_harness` re-export
  `crate::budget_run::deadline` behind the feature. That is uglier.

### 2. The new total deadline is 600 s: longer than the whole fast tier's budget, so the loop it guards against still runs 10 minutes (33)

- **Where:**
  - `crates/graft/tests/it/deadline.rs:13` (`DEADLINE = 600 s`).
  - Every fast-tier pump uses it: `app_harness.rs:241`, `commit_editor_writes.rs:127`, `changes_pane_writes.rs:116`,
    `m4_walk/run.rs:225`, `m5_walk/run.rs:481`.
- **What's wrong:**
  - PROMPT.md 7.1 gives the whole fast tier "under 3 minutes".
  - The ticket asked for "e.g. 60 s". The builder chose 600 s because `budget_run`'s per-event `PATIENCE` is 300 s.
    That reason only covers `budget_run`, a heavy-only file.
  - The loop this ticket fixed spun for 9 minutes. Under this guard it would still spin for 10 at 100 % CPU, on up
    to 4 test threads, before failing.
- **Why it matters:** laptop safety is the reason the guard exists (rule 2's "hang → named failure"). A guard longer
  than the tier it protects does not keep the machine usable.
- **Fix:** use two constants.
  - The harness's deadline, for the fast tier: for example 120 s, the same as its `PATIENCE`. A settling pump in
    this suite takes seconds; the slowest test is 15 s.
  - `budget_run`'s own, for the heavy tier: 600 s.

  Pass each where it's used. This is still a test guard, not a product cap.

### 2. A radar-context job that panics or can't start leaves the context `Pending` until `Ctrl+R`, with no pane line (33-q2)

  `jobs/pool.rs:179` and `:195`.

  draws. Every radar finding is silently absent, and the only word is a transient `<id> failed: …` status.
- **The same shape elsewhere:** an evil probe's `JobFailed` leaves `detail.evil` `Pending`. The pane then says
  "checking" (`view/radar.rs:187`) until the selection moves (`ops.rs:184-194`).
- **Why it matters:** rule 3. It is also the case ticket 33 set out to close ("no findings" read as "nothing wrong").
- **Fix:** in `job_failed`, set `radar.context = Failed(failure.to_string())` when it is `Pending(id)`, and the same
  for `detail.evil` (and the force-push/duplicates probes if they hold a `Pending(id)`). Red first with a
  `JobFailed(id, Panicked)` through `update`.
